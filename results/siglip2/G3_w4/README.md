# 4비트 가중치(MatMulNBits) 실험 — ORT 최종 위에 넓혀 보기 (2026-10-16)

**결론: 4비트는 크기를 105.3 → 73.6 MiB(−30%)까지 줄이고 정확도는 U8+rr과 통계적으로 동률이지만, 이 PC(x86) 4스레드에서 U8+rr보다 1.4~2.05배 느리다 (A 1.36·B 1.72·C 1.93·D 2.05배). C·D는 FP32와 비슷한 속도다. D-038 (나) 사전 기준(정확도 동률·속도 같거나 빠름·10% 이상 작음)을 모두 만족하는 구성이 없어 최종 모델에 넣지 않는다.** ORT 최종은 U8 + reduce_range 그대로다.

## 1. 왜 했나
대회 안내 4.1·6절이 INT4를 직접 언급한다 (기법 25·성능 개선 25). ORT 8비트 최종(D-030) 위에서 크기를 더 줄일 수 있는지 본다 (D-037).

## 2. 방법
- `siglip2/s2_quantize.py --w4-regex` (기본 꺼짐): 고른 MatMul 가중치를 MatMulNBits(4비트, 블록 32, 대칭, accuracy_level 4 = 활성값을 블록마다 int8로 동적 양자화해 정수 계산)로 바꾼 뒤, 나머지는 최종과 같은 U8+rr INT8 QDQ. 블록 5·9 fc2는 FP32 그대로.
- 구성: A 블록 MLP fc1 12개 / B + fc2 (22개) / C + attention qkv·proj (46개) / D + pooling head (51개)
- 0단계: 4비트 코드 추가 뒤 옵션을 끈 기본 경로로 U8+rr 최종을 다시 만들어 sha256이 기록값 `5eee7839…`와 **같음**을 확인 (`identity_check.txt`)
- 스크립트: `siglip2/scripts/w4_sweep.sh`(양자화 + 스크리닝), `s2_paired_ci.py`(dev 전체), `scripts/speed_w4.sh`(지연 3세션), `scripts/speed_w4_ab.sh`(A·B 1세션)
- 실패 기록 (숨기지 않음): 첫 세 번은 계산 전에 멈췄다 — ① sha256 비교 스크립트 버그(경로 역슬래시, 실제로는 SAME) ② 층 이름 정규식이 `^/blocks`로 고정돼 0개 ③ ORT 1.25 `nodes_to_include`가 "추가 포함"이라 53개 전부 4비트 → 개수 assert가 잡음, `nodes_to_exclude`로 고침

## 5. 해석
- **정확도·충실도**: 4비트 가중치(블록 32)는 정확도를 거의 잃지 않는다. cos는 오히려 오른다 (C 0.967 vs U8+rr 0.955). accuracy_level 4가 활성값을 블록마다 동적으로 int8 양자화해, 텐서 하나에 정적 눈금 하나인 QDQ보다 촘촘하기 때문으로 보인다 (추정 — 원인 분석의 "눈금 단위" 결론과 같은 방향, `../G3_why`).
- **속도**: MatMulNBits는 매 추론마다 가중치 풀기와 활성값 동적 양자화를 한다. ORT의 4비트 커널은 LLM의 토큰 1개씩(행 1개) 계산에 맞춰져 있고, 우리처럼 토큰 197개를 한 번에 곱하는 경우에는 VNNI int8 행렬곱(QLinearMatMul)보다 느린 것으로 보인다 (추정). 4비트로 바꾼 층이 많을수록 느려진다 (A +36% → D +105%).
- **보고서에 쓸 점**: "크기 −30%와 속도 −50%를 동시에 얻을 수 없었다 — 4비트는 CPU 커널 구현 때문에 속도를 잃는다." 대회 배점상 성능 개선은 속도·메모리·크기를 함께 보므로, 속도를 절반 잃고 크기 30%를 얻는 것은 손해로 판단했다.
- **Hailo와의 관계**: MatMulNBits는 ORT 전용이라 Hailo와 무관하다. Hailo-10H는 INT4를 하드웨어로 지원하므로(40 TOPS INT4) 본선에서 `a8_w4`(`siglip2/hailo/g4_D256L1_w4A/B.alls` 준비됨)를 따로 시험할 가치가 있다. 다만 칩에서 따로 확인해야 한다 (참고: 개인연구 세션이 폰 NPU에서 W4A16 모델이 PC와 달리 무너졌다고 알려 왔다 — 이 저장소의 raw로는 확인할 수 없는 전달 정보).
