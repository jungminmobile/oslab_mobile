# G4 DFC 스크리닝: 구성별 정확도를 ORT와 같은 사진으로 (2026-10-14)

**결론: DFC 구성 중에서는 C(Hailo 공식 패턴)와 D(공식 + 블록 9 fc2)가 동률로 가장 좋다 (고화질 cos 0.949·0.952, Δtop-1 −1.4·−1.1%p). 둘 다 ORT fc2L2(동률인 S8 세 후보 중 가장 작은 것, +0.3%p)보다 1.4~1.7%p 유의하게 낮다. E(블록 0·5·9 fc2만 16비트)는 −2.3%p로 유의한 손실이다.** 어떤 구성을 고를지는 팀이 정한다 (아래 "결정 필요").

## 1. 왜 했나

G4 첫 비교(`../G4_dfc_first`)는 Pets 64장뿐이었다. 그래서 cos 순위(D > C > E > B)와 top-1 순위(E > B > C = D)가 엇갈렸다.

ORT 스크리닝(D-024: dev 6종 × 앞 200장)과 **같은 사진, 같은 지표**로 다시 재야 두 가지를 할 수 있다.
- 구성끼리 짝 비교 (PRD 5절 짝 부트스트랩)
- ORT 정수 구성과의 직접 비교

## 2. 방법

- 에뮬레이션: DFC 5.4.0 `SDK_QUANTIZED`. `siglip2/hailo/s2_dfc_screen.py`가 데이터셋마다 `infer`를 한 번 부르고, 배치 8, WSL Ubuntu-22.04에서 공용 잠금 안에서 돈다.
- 사진: dev 6종(CIFAR A, Pets, Flowers, Cars, Food, Caltech) 각 앞 200장. ORT 스크리닝과 같은 캐시·같은 순서다.
- 기준: 같은 캐시의 FP32 ONNX 임베딩(`<key>_ref_fp32.npy`)이다. 지표는 고화질 5종 평균 cos(주)와 Δtop-1이다.
- 짝 비교: `siglip2/s2_compare_dfc_ort.py`. 사진별 예측 npz를 같은 사진끼리 짝지어 데이터셋별 층화 부트스트랩 1000회로 95% 구간을 냈다.
  - ORT 쪽은 G3 dev 전체 예측(`../G3_cumulative/full/pred_*.npz`)의 앞 200장이다.
  - 검증: ORT fc2L2를 이 방식으로 다시 계산하면 G3 스크리닝 값(cos 0.9557, +0.3, CIFAR −7.0)과 정확히 같다.
- 구성(`.alls`는 `siglip2/hailo/g4_*.alls`, 공통: 최적화 수준 0, 보정 64장, `[conv1]`·`{ew_add*}` 16비트):
  - C: 공식 패턴 = A + 블록 0·5의 fc1·fc2 (`conv4, conv5, conv24, conv25`)
  - D: C + 블록 9 fc2 (`conv41`)
  - E: A + 블록 0·5·9 fc2만 (`conv5, conv25, conv41`)
  - (A·B는 64장 비교에서 열세라 순서상 뒤로 미뤘고, 아침 결정으로 지연 측정을 먼저 하면서 돌리지 않았다)


## 4. 해석

- **64장에서 엇갈렸던 순위가 cos로는 정리됐다** (D ≥ C > E). top-1은 E가 낮지만 C·D와의 차이가 유의하지 않다 (C→E −0.9 [−2.3, +0.5], D→E −1.2 [−2.6, +0.1]). 64장에서 E의 top-1이 높았던 것(2장 차이)은 표본 잡음으로 보인다 (추정).
- **블록 9 fc2를 16비트로 더 두는 효과(D − C)는 200장×5종으로 구분되지 않는다** (+0.3, 구간 0 포함). ORT(G3)에서는 블록 9 fc2가 필수였다. 이유는 두 가지로 보인다. DFC는 잔차 합(`ew_add`)을 이미 16비트로 두므로, 블록 9 fc2 출력의 거대 값(`../G3_why` 2단계)이 잔차에 더해질 때 손실이 줄 수 있다. 또 DFC 양자화 방식(층별 보정)이 ORT와 다르다. **추정이며 확인하지 않았다.**
- **fc1을 8비트로 둔 E가 나쁜 이유**: C·D는 블록 0·5의 fc1과 fc2를 모두 16비트로 두고, E는 fc2만 16비트로 둔다. 블록 5의 fc2 입력(= fc1 → GELU 출력)에 거대 값이 처음 생기므로(`../G3_why`), fc1 출력을 8비트로 두면 그 신호가 이미 뭉개지는 것으로 보인다. 추정이다.
- **DFC가 ORT보다 1.4%p 낮은 이유** (가설, 확인 안 함):
  1. DFC 구성은 MatMul뿐 아니라 LayerNorm(분해)·Softmax 등도 8비트다. ORT fc2L2는 MatMul만 정수다.
  2. DFC는 최적화 수준 0(GPU 없음)이고 보정이 64장이다. ORT는 Percentile 256장이다.
- CIFAR A(저해상도)는 모든 구성에서 손실이 크다 (−7~−25%p). 주 지표가 아니다 (D-017).
