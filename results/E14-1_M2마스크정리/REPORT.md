### G2(c) 기준 수정 (계획과 다른 점 1)

원래 기준으로는 두 가지가 걸렸다. 둘 다 검사 기준을 잘못 정한 탓이고 모델 문제가 아니다.
1. **K 자리 7곳**(Sub_1·4·7·10·15·20·25): ORT_ENABLE_ALL 진단 사본에서는 **O 자신도** 중간 출력이 식 값과 0.025 달랐다. ORT 최적화가 그 중간 텐서 값을 바꾼다(그 텐서는 QuantizeLinear로 이어짐). ORT_DISABLE_ALL에서는 정확했다 (`e14/dbg_g2c.py`). 최종 임베딩은 진단 사본과 원래 모델이 같았다.
2. **O의 sink 오차 한계**: 원래 식 `X + (c − X)`의 반올림 오차 한계는 1 ulp(c)가 아니라 **1 ulp(max(|X|,|c|))**다. c 기준으로는 최대 2,464 ulp, max 기준으로는 27곳 모두 정확히 1.0이었다.

수정 기준(ORT_DISABLE_ALL, max 기준 ulp)으로 재실행(`--step g2c --disable-opt`, `g2c_disable.json`)한 결과: 27곳 모두 W1·W2 출력 = 정확한 선택 `where(m, c, Y)`, O의 sink 아닌 자리 = Y, sink 자리 오차 ≤ 1 ulp(max).

## 계획과 다른 점

1. G2(c) 기준 수정 (위).
2. **비단순 6개를 모두 바꿨다.** 6개는 같은 X를 쓰는 두 마스크가 이어진 체인(15번 토큰 → 7번 토큰)이었다. Add 입력 Y는 앞 마스크 출력이라 X와 이름이 다르다. 하지만 두 마스크의 1인 자리가 겹치지 않아(상수로 확인, overlap 0) 뒷 마스크가 1인 자리에서 Y = X가 정확히 성립한다. 그래서 같은 선택 연산으로 보고 바꿨고, G2(c) 수정 기준으로 실행 확인했다. 계획서 3절 규칙 1의 "형태 연산만 거쳐 값이 같음"을 이 경우까지 넓혀 해석한 것이다.
3. 메모리는 E12-1 `bench_mem_session.py` 대신 `e14/mem_child.py`(같은 정의, 입력만 B/32용 256 dev 캐시)를 썼다. 반복마다 모델 순서를 바꿨다(O W1 W2 / W2 W1 O / O W1 W2).
4. 지연 자식은 `e12/e12_4_speed.py`(A0 = C3 + 스레드 풀 기본값, EcoQoS 끔)를 그대로 썼다. 3세션은 최소화 창 하나에서 120초 간격으로 연달아 실행했다. 모든 행 throttle_off true.
5. `e14/peek.py`(그래프 첫 확인용)는 삭제 권한이 없어 남겨 두고 함께 커밋했다.

## 해석

- **W2(노드 54개 감소)가 W1(27개 감소)보다 느렸다.** ORT CPU의 `Where`(bool 마스크 브로드캐스트)가 Mul·Add 2개보다 싸지 않다. 노드 수 감소가 곧 속도는 아니다.
- **W1의 실측(−1.5%)은 오버헤드 보정 기대치(−2.2%)보다 작다.** Sub 1개를 빼도 그 자리의 Mul이 같은 크기 텐서를 그대로 처리하므로, 줄어든 것은 원소별 연산 1번분과 스레드 고정비 정도다.
- W1은 상수 5.3 MB로 파일 +5.1%, peak +1.9%. 속도 이득이 기준선 수준이라 이 비용을 정당화하기 어렵다.
- 수치는 O와 비트 단위로 같다 → 이 정리는 정확도에 아무 영향이 없다. 나중에 다른 기법과 함께 쓸 수는 있다.
