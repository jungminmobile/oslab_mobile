# E14-1 M2 마스크 식 정리 — 결과 보고

> **결론: 효과 없음 → 제출 모델 O 그대로 유지.** 마스크 식 27곳을 정리해도 4T 지연이 W1 −1.50%, W2 −0.68%로 기준(−1.5% 이상 감소)에 못 미쳤다. 정확도는 O와 **비트 단위로 같다**. 다음 E14-2(GELU 융합)는 O 위에서 한다.

| 항목 | 내용 |
|---|---|
| 실행 | 2026-10-23 02:55~03:20, 정민 노트북 (Core Ultra 7 258V, Windows, Python 3.11.9 / ORT 1.25.0), 전원 연결 |
| 기준 모델 O | 현재 **제출 모델** B/32 O-AB (INT8 양자화, sha `7a01044c…dbf6`). FP32 원본이 아님 |
| 비교 모델 | W1 = 마스크 식을 Mul·Add로 / W2 = Where로 바꾼 것 (O에서 27곳만 수정) |
| 데이터 | dev만 (test 안 씀) |
| 코드·커밋 | `oslab_mobile/e14/`, 브랜치 `jungmin/e14-graph`, 로컬 커밋 `1e6f628` |

## 1. 한눈에 보기

| | O (제출) | W1 (Mul·Add) | W2 (Where) |
|---|---|---|---|
| **4T 지연 p50** | 16.41 ms | 16.18 ms (**−1.50%**) | 16.30 ms (**−0.68%**) |
| 2T 지연 p50 | 22.25 ms | 21.93 ms (−1.4%) | 22.05 ms (−1.4%) |
| 1T 지연 p50 | 38.85 ms | 38.27 ms (−0.7%) | 38.53 ms (−0.8%) |
| **정확도** (dev 1,200장) | 고화질 89.30% | O와 **비트 일치** | O와 **비트 일치** |
| **최대 메모리** | 239.4 MiB | 244.0 MiB (+1.9%) | 239.0 MiB (−0.2%) |
| 파일 크기 | 98.0 MiB | 103.0 MiB (+5.1%) | 98.0 MiB |
| 노드 수 (ORT 최적화 후) | 597 | 570 | 543 |
| **판정** | — | **효과 없음** | **효과 없음** |

- 지연은 3세션 중앙값, 비율은 같은 세션 안 O 대비 비율의 중앙값.
- W1의 실제 값은 −1.496%로, 기준 −1.5%에 0.004%p 못 미쳤다. 세션 간 흔들림이 이보다 커서 "빨라졌다"고 말할 수 없다. 사전 등록 규칙대로 판정했다.

## 2. 무엇을 배웠나

1. **노드를 줄여도 빨라지지 않을 수 있다.** W2는 노드를 54개 줄였지만 27개 줄인 W1보다 느렸다. ORT CPU에서 `Where` 1개가 `Mul`·`Add` 2개보다 싸지 않다.
2. **실제 이득은 기대치보다 작았다.** W1 기대 −2.2% → 실측 −1.5%. Sub 1개를 빼도 남은 Mul이 같은 크기 텐서를 그대로 처리한다.
3. **W1은 비용도 있다.** 미리 계산한 상수(`m·c`) 때문에 파일 +5.3 MB, 메모리 +1.9%(허용선 +2% 바로 아래).
4. **정확도 영향은 0이다.** 원래 식의 미세한 반올림 차이가 바로 다음 양자화 단계에서 사라져, 최종 임베딩이 1,200장 모두 O와 비트 단위로 같았다.

## 5. 계획과 다르게 한 것

| # | 무엇 | 왜 |
|---|---|---|
| 1 | **G2(c) 기준 수정** (정민 승인 03:07) | 원래 기준이 잘못 정해져 있었다. ① K 자리 7곳은 ORT 최적화를 켜면 O 자신의 중간값도 식과 달라 보였다(최적화 끄면 정확) → 중간값 검사는 ORT 최적화를 끄고 한다. ② 원래 식의 오차 한계는 "c 기준 1 ulp"가 아니라 "max(\|X\|,\|c\|) 기준 1 ulp" → 고친 기준으로 27곳 모두 통과 |
| 2 | **비단순 6곳도 모두 바꿈** | 6곳은 같은 입력을 쓰는 마스크 2개가 이어진 구조(15번 토큰 → 7번 토큰)였고, 두 마스크가 겹치지 않아 수학적으로 같은 선택 연산이다 |
