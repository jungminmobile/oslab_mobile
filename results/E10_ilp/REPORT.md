## 요약
- **질문**: 민감한 블록부터 하나씩 FP32로 되돌려 고른 지금 최종(B2, 탐욕법) 대신, 같은 지연 예산 안에서 정확도 손실이 최소가 되도록 정수계획으로 한꺼번에 고르면 더 빠르거나 작은 구성을 찾을 수 있는가?
- **방법**: 단위 23개(X.0 블록은 3지선다)의 민감도·지연·크기를 실측 → 7개 지연 예산에서 다중선택 배낭 동적계획으로 구성 선택(P1~P7) → B2와 같은 밤, 같은 기기에서 dev 전체 정확도·1/2/4스레드 지연(3세션)·메모리 실측 → 결과 전에 고정한 4개 조건으로 판정.
- **결과**: 7개 구성 모두 정확도는 B2와 동률(①통과)이지만, **1·2·4스레드 모두 B2보다 느리고(② 실패), 크기·메모리도 더 크다(③ 실패)**.
- **해석**: CNN에서는 층별 민감도가 더해지지 않는다(stem·L1.0은 하나씩이면 나빠지고 묶어야 좋아짐). 또 단위별 지연 차이가 노트북 측정 잡음과 비슷하다. 그래서 정수계획이 B2 같은 "묶음 해"를 찾지 못했다.
- **의의**: 최종(B2)을 바꾸지는 못했지만, "체계적 최적화로 찾아도 B2가 최선에 가깝다"는 근거가 된다.

## 1. 배경과 질문
- 지금 RN50 최종 B2는 E4-B에서 "민감도 순서대로 하나씩 FP32로 되돌리기(탐욕법)"로 골랐다. stem과 L1.0 블록을 FP32로 두고 나머지는 INT8이다.
- 탐욕법의 한계로 지적된 두 가지:
  1. 비용(지연·크기)을 보지 않는다.
  2. 단위가 거칠다(블록 통째로 되돌림).
- HAWQ-V3(Yao et al., ICML 2021)의 방식을 가져왔다: **단위별 비용을 실측 → 예산 아래 민감도 합 최소화 정수계획 → 예산별 구성**. 민감도는 Hessian 대신 실측 cos 변화를 쓴다.

## 2. 방법

### 2-1. 고정 조건 (지금 최종과 같음)
| 항목 | 값 |
|---|---|
| 원본 | `rn50_image_fp32_q1.onnx` |
| 양자화 | ORT 정적 QDQ, U8S8, 가중치 채널별, Percentile 99.999, 보정 고화질 256장 시드 0 |
| 바뀌는 것 | 단위별 FP32/INT8 선택만 (`--exclude-exact`) |
| 기준(B0) | 전부 INT8, attention 계산(QKᵀ·softmax·AV)만 FP32 |
| 비교 기준 | 노트북 B2, sha256 `687097928a9d82146d486f440e9956ab51d0ebacfffdf34c37e2c432dd3f19cd` |

### 2-2. 단위 정의 (23개, 결과 전 계획서에서 조정)
| 종류 | 단위 | 비고 |
|---|---|---|
| stem 3 | stem.c1 / c2 / c3 | conv + 뒤의 ReLU (c3는 avgpool 포함) |
| X.0 그룹 4 (X=1..4) | {INT8 / `LX.0.ds` / `LX.0.full`} 중 하나 | ds = downsample 노드 + 그 블록 Add, full = 블록 전체 |
| 둔감 블록 12 | L1.1 L1.2 L2.1~L2.3 L3.1~L3.5 L4.1 L4.2 | 블록 전체 |
| AttnPool 4 | AP.q / k / v / c | 투영 하나씩 |
- **계획서(35단위)에서 바꾼 이유**: X.0 블록의 conv1~3을 하나씩 FP32로 되돌리면 ORT 정수 커널에서 정확도가 붕괴한다(E4-D: C2 −7.12, C3 −8.59%p). 그래서 블록 안 conv는 묶고, 덧셈 FP32로 안전함이 확인된 downsample만 따로 두었다.

### 2-3. 정수계획
- 변수: 그룹마다 INT8 또는 선택지 하나를 FP32로.
- 가치 s_u: B0에서 u만 FP32로 바꿨을 때 cos 증가분 (CIFAR A + Pets dev, 정수 커널 4T, 두 세트 cos 평균).
- 무게 t_u: u를 FP32로 바꿨을 때 4스레드 지연 증가분 (같은 실행 안의 B0와의 차). 0.05 ms 단위, 음수는 0으로.
- 예산: B0 4T 지연 × r, r = 1.013 / 1.052 / 1.091 / 1.130 / 1.169 / 1.247 / 1.325. 계획서의 절대 예산(13.0~17.0 ms)을 노트북 속도 변동 때문에 비율로 바꿨다.
- 풀이: 다중선택 배낭 동적계획(numpy). 검증으로 3⁴ × 2¹⁹ = 42,467,328가지 전수 탐색과 비교했다.

### 2-4. 측정
| 단계 | 내용 |
|---|---|
| 비용표 | 4T, n=100. 한 실행에 B0 + 단위 모델 7개를 번갈아. 첫 측정 후 B0 흔들림(1.86 ms)이 |t_u| 중앙값(1.12 ms)보다 커서, 규칙대로 3회 다시 재서 중앙값 사용 |
| 정확도 | dev 전체(CIFAR A 1000 + 고화질 5종 약 4,900장), 정수 커널 4T, B2 대비 짝 부트스트랩 1000회 데이터셋별 층화 |
| 지연 | `bench_speed` n=200, warmup 20, repeats 3. 1·2·4스레드 × 3세션, 한 실행에서 FP32·B2·P1~P7 번갈아. 세션 사이 2분 냉각. 3세션 중앙값 |
| 메모리 | `bench_mem` 4T, 모델마다 새 프로세스 peak RSS |

## 4. 분석: 왜 정수계획이 졌나
1. **민감도가 더해지지 않는다 (CNN의 정수 커널 경계 효과)**: stem.c2나 L1.0을 하나만 FP32로 두면, 8비트 사이에 FP32 섬이 생겨 ORT 정수 커널에서 오히려 나빠진다(E4-B의 B1, E4-D와 같은 현상). 묶어서 FP32로 둬야 좋아진다. "단위별 효과의 합"을 최적화하는 정수계획은 이런 묶음 해를 원리상 찾을 수 없다.
2. **단위별 지연(0.5~3 ms)이 측정 잡음(±2~3 ms)과 비슷하다**: 3회 중앙값에서도 일부 큰 블록의 t_u가 0 아래로 나왔다. 정수계획이 이를 "공짜"로 보고 L2.3·L3.1·L3.5를 골랐고, 실제로는 크기 +13 MiB와 지연 증가로 이어졌다.
3. **B2는 이미 싼 곳만 FP32로 둔다**: stem·L1.0은 연산량과 가중치가 작다. 그래서 탐욕법의 "비용을 보지 않는다"는 한계가 RN50에서는 실제 손해로 나타나지 않았다.

## 5. 결론
- **채택 없음. RN50 예선 최종은 B2(4T 2.0~2.2배, 37.7 MiB, 고화질 −1.05(클라우드)/−1.43(노트북)%p) 유지.**
- 보고서용 문장: "탐욕법으로 고른 B2를 HAWQ-V3식 지연 예산 정수계획과 사전 등록 규칙으로 비교했다. CNN의 정수 커널 경계 효과로 층별 민감도가 더해지지 않고 단위 지연이 측정 잡음 수준이어서, 7개 예산 모두에서 B2보다 빠르거나 작은 구성이 없었다. 이는 B2가 이 조건에서 최선에 가깝다는 근거다."
- SigLIP2와의 대비(보고서 CNN vs ViT 분석용): SigLIP2는 잔차·LayerNorm이 FP32로 고정돼 정수 경계 문제가 없고 단위(MatMul) 효과가 상대적으로 독립적이다 → G7(준혁)에서 정수계획이 다르게 작동할 수 있다.

## 6. 한계
- 노트북 측정 잡음이 커서 t_u가 부정확했다. 정밀한 측정(예: n 증가, 여러 회 반복)으로 다시 해도 결론이 바뀔지는 확인하지 못했다. 다만 B2가 이미 싼 곳만 FP32로 둬서 이득 여지는 작다.
- 민감도 스크리닝은 CIFAR A + Pets 두 세트만 썼다(E4와 같은 방식).
- 이날 노트북 절대 속도는 10/17보다 약 1.5~1.8배 느렸다(B2 4T 15.1 → 23.3 ms). 판정은 같은 밤 비교라 영향 없음. 다른 날 ms와 직접 비교하지 않는다.
- 파레토 그림은 만들지 않았다(다른 날 측정점을 섞지 않기 위해 표로 대신).
