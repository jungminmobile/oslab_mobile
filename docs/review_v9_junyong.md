## 0. 5줄 요약

1. **그림 F1·F2 범례가 "B/16 (제출) / B/32 (비교)"로 되어 있다.** 제출 모델이 틀렸고, "두 모델 비교"로 읽힌다. 가장 먼저 고쳐야 한다.
2. **B/16이 본문 곳곳에서 비교 대상으로 쓰인다**(2장 요약, 3.2-3·4, 10장 전체, F1·F2·F4b, 6.4 이상치 기준 모델). 10장은 부록의 3~4줄로 줄이고, 그림은 B/32만 남긴다.
3. **Hailo는 서술이 바뀐 상태를 반영하지 못했다.** 본선 HEF를 "GF·ALL8F 중 팀이 정함"으로 써서 변경 가능성처럼 읽힌다. 컴파일 설정 출처(Zoo 레시피)가 없고, 실칩 결과가 본문(3.3)에 섞여 있으며, Hailo test(+2.73)와 test 사용 이력이 빠졌다.
4. **채점 조건이 덜 적혔고, 지난 사실이 남아 있다.** `enable_mem_pattern`이 언급되지 않는다. 비상 대체 파일 M2rot `3a46ae8a…`는 Release에 있다는 기록이 없다(Release에는 `9783d7de…`). ARM 결과(26장, 2.2%)가 "확인 안 함"으로 남아 있다.
5. 숫자는 대부분 원자료와 맞는다(약 120개 대조, 틀린 값 없음). 다만 다음이 남아 있다.
   - 대표 속도는 10/22 낮 값이고, 팀 사실표는 10/23 새벽 값이다.
   - 출처 파일이 없는 숫자가 3개다(92.10M, 0.16M, Q/DQ 노드 수).
   - 추정을 사실처럼 쓴 문장이 3곳이다.

### M4. 컴파일 설정을 우리 기법처럼 썼다 — 출처 없음
- 위치: 3.3 표 L97 "**GF**: G + 컴파일 설정 2줄", L85 혼합 정밀도 행. `resources_param`은 본문 어디에도 없다.
- 사실 (원자료):
  - G의 `.alls`에는 **Zoo B/32 v5.4.0 .alls의 `resources_param`** 줄이 있다(G6b `M_rb`·`M_both` → G6d G).
  - GF의 두 줄 `allocator_param`·`context_switch_param`은 **Zoo v5.4.0 `clip_vit_b_16_image_encoder.alls`**에서 그대로 가져왔다(G6d L19·L25, G6f L17).
  - 두 줄은 출력을 바꾸지 않고(1,200장 비트 동일) 지연만 줄였다(G6d F − M_both −1.84 ms, G6f G → GF −0.70 ms).
- 고칠 문장 제안 (3.3 표 아래 주석으로):
  > "컴파일 자원 설정은 Hailo Model Zoo v5.4.0 레시피에서 가져왔다. `resources_param`은 SigLIP2 B/32 레시피에서, `allocator_param`·`context_switch_param`은 CLIP ViT-B/16 레시피에서 가져왔다. 이 설정은 양자화 결과를 바꾸지 않는다(G와 GF 출력 1,200장 비트 동일). 우리 기여는 16비트 보호층을 줄인 것이다. 회전·레지스터 캐시로 거대 활성값을 없앴기 때문에 Zoo가 16비트로 두는 블록 0·5 MLP 층(`conv3·4·5·25`)도 8비트로 내릴 수 있었다(G)."
- 표 GF 행 이름도 "G + Zoo 컴파일 설정 2줄"로 바꾼다.

### M7. 채점 환경 조건이 덜 적혔다
1. **`enable_mem_pattern=False`가 보고서에 없다.**
   - README L100은 "제출 실행 스크립트에 넣을지는 팀이 정한다"고 되어 있다. 이 브랜치의 `cross_latency.py`·`portable_eval.py`·평가 스크립트에는 이 옵션이 없다. 따라서 보고서의 메모리 −57.5%는 **기본 세션** 값이다.
   - 팀이 끄기로 했다면 세 군데에 조건을 적는다: (a) 어느 스크립트에 넣었는지, (b) "우리 실행 스크립트로 실행할 때만 적용되며 채점 측이 직접 세션을 만들면 적용되지 않는다", (c) 메모리 수치가 어느 설정 값인지.
   - 4.2·8장 4번·9.4에 한 줄씩 넣는다. 예: "메모리는 ORT 기본 세션 값이다. 우리 스크립트는 `enable_mem_pattern=False`를 쓰며(정민 E12-1, 출력 비트 동일), 이때 메모리가 약 9% 더 준다. 이 옵션은 채점 측이 세션을 직접 만들면 적용되지 않는다."
2. **비상 대체 ONNX가 Release에 없다(기록상).**
   - 7.1-2 L326과 D-049는 ORT 미사용 시 대체 파일을 준용 바탕 M2rot `3a46ae8a…`로 정했다.
   - 그런데 Release 묶음(`b32/xplat/README_bundle.md` L11, README L17)에 든 M2rot은 이 PC 빌드 `9783d7de…`다. 7.1-2 스스로 "회전 행렬이 달라 본선 연속성이 깨진다"고 한 파일이다.
   - `3a46ae8a`를 Release에 올렸다는 기록은 찾지 못했다(`b32-portable-junyong`이 추가한 것은 `23236123`·`79e797c1`·`506e9fe4`).
   - → `3a46ae8a`를 Release에 올리고 sha256을 8장에 적는다. 그 전까지 README·보고서에 `9783d7de`를 "대체 파일"처럼 읽히게 두지 않는다. 지금 README L17은 "(비교용)"이라 괜찮다.
3. 7.1-2·9.4-2는 "onnxruntime 전용"을 잘 적었다. 다만 8장 4번(L355)에도 "**onnxruntime 1.25.0에서만 실행 가능**(com.microsoft 연산)"을 굵게 한 번 더 적기를 권한다.

## 2. 고치면 좋은 것 (근거 보강·표현)

### G1. 기법 깊이(25점): "원인 → 처방 → 16비트 보호 제거 → Zoo 추월" 사슬을 한 문단으로
- 지금: CPU 쪽 진단(5.3 단계 2~5)은 아주 좋다. Hailo 쪽은 3.3 표의 M·G·GF 행 이름에만 묻혀 있어 인과가 안 보인다.
- 원자료로 바로 쓸 수 있는 사슬:
  1. **Zoo가 16비트로 지키는 층 = 우리 민감도 지도가 찾은 층.** Zoo B/32 .alls의 16비트 conv는 `conv3·4·5`(블록 0 attention 투영·fc1·fc2)와 `conv25`(블록 5 fc2)다(G6b L24). 우리 민감도 지도의 붕괴 블록도 0과 5부터다(5.3 단계 2). 벤더가 독립적으로 같은 층을 지킨 것이다. 원인 진단을 바깥에서 받쳐 주는 근거다.
  2. **정확도 이득은 레시피가 아니라 sink 처방에서 온다.**
     - Zoo 레시피 그대로 회전만 넣은 S1은 Zoo와 동률이다(+0.65 [−0.19, +1.46]).
     - 같은 레시피에 sink 처방을 더한 S2는 +2.12 [+1.37, +2.89] 우위다(G6d 표).
     - 그래프 출처(open_clip vs Zoo ONNX)는 차이가 없었다(S1 − Vrot +0.13 동률).
  3. **처방 덕분에 16비트 보호를 걷어낼 수 있다.**
     - 우리 넓은 보호(M)를 Zoo 집합으로 줄여도 동률이다(M_z16 − M −0.21 [−0.70, +0.30], G6b).
     - Zoo가 지키는 블록 0·5 층까지 8비트로 내린 G는 Zoo보다 +2.67 [+1.92, +3.46] 정확하면서 −5.0% 빠르다(G6d).
  4. **벤더 컴파일 설정까지 맞추면 속도에서도 Zoo를 넘는다.** GF는 G와 출력이 비트 동일하고 −9.5%다(G6f).
  5. **절제:** 잔차 덧셈까지 8비트(ALL8F)는 −18.9%로 더 빠르지만 GF 대비 −0.87 [−1.46, −0.28] 열위다. → 남은 16비트(패치 경로·잔차 26개)는 필요하다.
- 주의:
  - G − M_both 쌍 비교 구간은 G6d 표에 없다. 점추정은 −1.55 vs −1.05다. G6d 결론표 L205는 "M_both와 동률"이라고만 적었다. 보고서에 "동률"을 쓰려면 구간을 먼저 확인하거나, "Zoo보다 +2.67 우위"만 쓴다.
  - 이 사슬은 실칩 결과라 부록 F에 둔다(M6). 본문 5장에는 1번(벤더 16비트 층 = 우리 민감도 층)만 넣어도 기법 깊이에 도움이 된다. 1번은 실칩 숫자가 아니라 `.alls` 내용이라 본문에 둬도 된다.
