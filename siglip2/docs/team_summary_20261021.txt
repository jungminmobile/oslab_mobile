【1. 지금까지 한 것 (시간 순)】
━━━━━━━━━━━━━━━━━━━━

▶ G0~G1 (10/13) 시작·출발점
- 모델: SigLIP2 ViT-B/16 224 (timm/open_clip), 토큰 196개, 블록 12개, 파라미터 92.9M, 35.45 GFLOPs
- 범위: 이미지 인코더만 양자화, 텍스트는 클래스 문장 임베딩을 FP32로 한 번 계산해서 재사용
- ONNX로 내보내기 → PyTorch와 출력 같음 확인
- 단순 INT8(MinMax, 모든 연산)은 정확도 91.66% → 1.37%로 붕괴
- Hailo DFC 기본 8비트도 cos 0.12로 붕괴

▶ G2 FP32 기준
- dev(train에서 뗀 구간) 고화질 5종 평균 91.66%, CIFAR 76.9%
- 프롬프트: CLIP 공식 템플릿이 SigLIP 권장보다 1.53%p 좋아서 CLIP 템플릿 사용
- 측정 규칙(RN50 트랙과 공통): 정수 커널만, dev로만 고르고 test는 최종 1회, 짝 부트스트랩 95% 구간, 속도는 워밍업 20 + 200장×3회 번갈아

▶ G3 원인 찾기와 첫 해결
- 민감도 지도: 블록 하나씩만 INT8 → 블록 5~11이 하나만 INT8이어도 붕괴, 연산 중에는 MLP fc2가 원인
- 원인 분석: 블록 5·9의 MLP가 고정 위치 패치 토큰(55, 13)의 특정 채널 4개(67·301·145·483)에 거대한 값을 씀 (attention sink, 다른 토큰이 attention의 27~52%를 여기에 몰아줌)
  → 텐서당 눈금 1개인 8비트에서 이 값이 눈금을 넓혀 그 층 출력이 무너짐
  → 토큰별·채널별 눈금이면 회복(cos 0.999): "8비트가 부족한 게 아니라 눈금 단위가 안 맞는 것"
- 보정 방법 비교: Percentile 99.999가 최선 (MinMax·Entropy보다 좋음)
- 혼합 정밀도: 블록 5·9의 fc2 두 층만 FP32로 두면 충분
- 활성값 형식: S8은 x86에서 QKV가 정수로 안 합쳐져 거의 안 빨라짐 → U8 + reduce_range로 약 2배
- 이 단계 결과 "R0": dev −0.78%p, test −0.83%p (10/17, test 1회 사용)
- 4비트 가중치: 크기 −30%까지 줄지만 x86에서 1.4~2배 느려져 미채택 (D-039)
- 다른 CPU 재현: 같은 파일이 x86 세 세대에서 비트 단위로 같은 출력, ARM(Orin)도 정확도 같음

▶ G4 Hailo 이식 (쭈리 PC WSL + 정민 노트북 교차 확인)
- DFC 5.4.0으로 HEF 컴파일 성공
- 원인 층(블록 0·5 MLP, 블록 9 fc2, 잔차 덧셈)만 16비트로 두는 설정(D256L1) 선택
- 보정 256장 + optimization_level 1로 에뮬레이터 cos 0.949 → 0.967

▶ 준용형 실험으로 원인을 직접 고침 (G3Q·G3R·G3RQ, 10/18~19)
- 회전(채널 축): 잔차 흐름을 직교 행렬로 돌려 4개 채널에 몰린 값을 768채널에 퍼뜨림 (수학적으로 같은 모델)
- 레지스터 캐시 M2(토큰 축): sink 토큰의 K·V와 MLP 입력을 보정 데이터 평균 상수로 바꿈
- 둘을 합친 M2rot: fc2 예외 없이 행렬곱 79개 전부 INT8로도 R0보다 정확 → 예선 모델로 교체 (D-044, test 보기 전에 확정)
- 최종 결과(10/20): dev −0.23 [−0.64, +0.18], test −0.34 [−0.50, −0.18], 크기 −74.1%, 4스레드 지연 −49.9%, 메모리 −51.7%
- Hailo 실칩: −1.79 → 회전 −0.94 → M2rot −0.41%p

▶ G6 다른 기기 확인
- 같은 제출 파일이 i7(쭈리)·Ultra 9 285K(준용)·Ultra 7 258V(정민)에서 같은 결과, 개선율도 기기마다 비슷 (−50~63%)

▶ G8 후보 비교와 보고서용 실험 (10/20~21, 쭈리 PC)
[B/16 보고서용 실험]
- A1 기법별 단독 효과 2×2 (전부 INT8): 원래 −63.5 / 회전만 −49.0 / M2만 −0.62 / 회전+M2 −0.31 → M2(토큰 축)가 결정적
- A2 새 가상환경 재현: 같은 PC면 최종 파일까지 비트 단위로 같음, 다른 PC와는 회전 행렬 계산부터 다름
- A3 소규모 평가 묶음(dev 6종×200장, 저장소 없이 실행): 기대값 cos 0.9756
- A4 보고서 2장 숫자: 371.67 → 96.18 MB, FPS 3.97 → 7.93, 피크 456.9 → 220.7 MB, p50·p95
- A5 CPU 저장 형식 3가지: 최대 −2.1%라 기준(15%) 미달 → 예선 모델 그대로
- ORT 프로파일링: 남은 변환 비용 최대 13% → 형식으로는 못 줄임
[B/32 반복 실험 — 준용형이 한 것은 빼고]
- B/16과 같은 원인(같은 채널, sink 토큰 15·7), 같은 패턴(블록 5부터 붕괴, fc2가 원인), B/32만 블록 0도 민감
- 같은 처방이 통함: 원래 −61.0 → M2만 −1.58 → 회전+M2 −0.79%p (준용형 PC −0.87과 일치)
- 블록 0 보호 시도: cos는 오르지만 사전 기준 미달 → 미채택
- 같은 PC 같은 실행 지연: B/16 84.0 ms vs B/32 32.0 ms (4스레드)
[결정]
- D-045 (팀): RN50 제외, SigLIP2만
- 학술부 답: 성능은 원본 대비 개선율로 채점
- D-046: 예선 = B/16 유지 (개선율은 B/32와 비슷하고 정확도 손실이 더 작음, test·재현 문서 완료). B/32는 "같은 방법이 다른 모델에도 통한다"는 일반화 근거로 보고서에
- D-047: 본선 HEF = B16_rb_bk (준용형 G6c: 컴파일 설정만 바꿔 출력 같고 47.6 → 40.5 ms)
[10/21 저녁 추가 확인 실험]
- E1 최종 파일로 dev 다시: −0.23 그대로 재현, 틀린 사진은 원래 헷갈리는 쌍(벤틀리 연식, 비슷한 꽃·견종)에 흩어짐
- E2 다른 PC 파일로 재현: 양자화만 해도 다른 파일 → "채점·재현은 배포 INT8 파일로" 확정
- E3 재현 절차를 빈 폴더에서 그대로: sha256 일치, 기대값과 같음 (명령 오류 1개 찾아서 고침)
- E4·E4b 처방이 실제로 한 일(출력 SNR): 블록 9 fc2 0.3 dB → M2 뒤 27 dB, 회전은 fc1·QKV +10~20 dB
  → 정확도와 맞는 건 "가장 나쁜 층의 SNR" (회전만은 평균이 높아도 한 층이 0.3 dB라 붕괴)
  → 원래 설명("값 84~99%가 0으로 반올림")은 원인이 아니었음을 발견해서 보고서 설명을 정정
- E5 보정 시드 0·1·2 + 빌드 PC: dev −0.23 ~ −0.49 (시드끼리 차이 유의하지 않음). 제출 파일은 좋은 쪽 끝이라고 정직하게 적음
