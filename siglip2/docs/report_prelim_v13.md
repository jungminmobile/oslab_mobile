## 2. 결과 요약

정확도는 제로샷 분류 Top-1이고, 고화질 데이터셋 5종(Pets, Flowers, Cars, Food, Caltech)의 test 평균을 주 지표로 썼다. 효율은 Intel i7-1165G7 노트북에서 배치 1, ONNX Runtime 1.25.0으로 잰 값이다. 제출 실행 스크립트와 같은 세션 설정(`enable_mem_pattern=False`)으로 원본(FP32)과 최적화 모델을 같은 실행 안에서 번갈아 쟀다(6.4). 아래에서 "제출 모델"은 최종 INT8 모델(파일 `e14_4_P2_patch_int8.onnx`)을 뜻한다.

|---|---|---|---|
| 모델 크기 (MB) | 378.36 | 95.65 | **−74.7%** |
| 파라미터 수 (M) | 94.55 | 94.54 (행렬곱 가중치 94.37M을 INT8로 저장) | −0.02% |

**요약.**
- SigLIP2 B/32의 이미지 인코더를 INT8 정적 사후 양자화(PTQ)로 최적화했다. 원본 가중치는 일부러 다시 학습하지 않았다(이유는 5.3).
- Transformer는 INT8로 바꾸기 어렵다. 많은 모델이 단순 INT8로도 손실이 1%p 안쪽이지만[9], Transformer는 일부 토큰·채널에 거대 활성값이 생겨[2][3] 텐서마다 눈금 하나로는 담을 수 없다. 이 모델도 단순 INT8에서 정확도가 61%p 떨어졌고, Hailo가 공개한 같은 모델의 HEF조차 FP32보다 dev 정확도가 4.22%p 낮다. 우리는 거대 활성값을 만드는 토큰 두 개를 찾아 레지스터 캐시와 Hadamard 회전으로 없앴다.
- 대회의 최종 목표인 NPU 이식은 본선 과제지만, 예선 단계에서 이미 같은 모델을 Hailo-10H용 HEF로 컴파일해 실칩(Jetson AGX Orin에 연결)에서 정확도와 지연을 쟀다. Hailo가 공개한 같은 모델의 HEF보다 지연은 9.5% 짧고 test 정확도는 2.73%p 높다(3.3, 부록 B). 잔차·패치 경로까지 모두 8비트로 내린 HEF는 공개 HEF보다 지연이 18.9% 짧으면서 정확도도 여전히 높았다(dev +1.80%p)².
- CPU 제출 모델은 ONNX Runtime 정수 커널에 맞춰 그래프를 네 군데 더 고쳐 속도를 올렸다. 패치 임베딩을 포함한 행렬곱 80개가 모두 INT8이다.
- 결과는 크기 −74.7%(INT8로 줄일 수 있는 한계 −75%에 거의 닿음), 지연 4스레드 −62.9%·1스레드 −68.0%, 메모리 −63.4%이고, 그러면서도 test 정확도 손실은 0.20%p다. 정확도를 지키는 흔한 방법인 "문제 층만 FP32로 남기기"는 같은 모델에서 dev 손실이 2.36%p였다(5.3).
- **5분 확인:** Release에서 파일 9개(스크립트 1, npz 6, ONNX 2, 약 1.4 GB)를 받아 `portable_eval.py`를 한 번 실행하면 FP32와 제출 모델의 정확도·코사인 유사도를 바로 비교할 수 있다(9.2 (가), Windows 명령 포함).

² HEF마다 16비트로 남긴 층이 달라 정확도와 지연이 다르다. 본선 HEF는 정확도를 우선해 잔차를 16비트로 남긴 구성이고(공개 HEF 대비 test +2.73%p, 지연 −9.5%. test는 우리 HEF 중 이것으로만 한 번 쟀다), 모두 8비트인 HEF는 지연을 우선한 비교 구성이다(dev는 FP32 대비 −2.42%p로 본선 HEF보다 0.87%p 낮음, 부록 B.1·B.3).

모델은 사진을 32×32 패치로 잘라 토큰 64개를 만들고, 폭 768의 Transformer 블록 12개를 거쳐 768차원 임베딩을 낸다. 파라미터는 94,552,320개, 연산량은 11.50 GFLOPs다. 텍스트 쪽은 클래스 이름의 임베딩을 FP32로 한 번만 계산해 두면 되므로, 기기에서 사진마다 실행되는 이미지 인코더만 양자화했다.

### 3.2 선정 사유

1. **엣지에서 쓸 곳이 많다.** 사진 임베딩 하나로 분류·검색·필터링을 다 하고, 클래스가 바뀌어도 텍스트만 바꾸면 된다.
2. **최신 모델인데 무겁다.** SigLIP2(2025)는 CLIP 계열의 최신 모델이지만 FP32 이미지 인코더가 378 MB이고, 노트북 1스레드에서 사진 한 장에 120 ms 넘게 걸린다.
3. **Transformer라 양자화가 어렵다.** 거대 활성값 때문에 단순 INT8로는 정확도가 무너지고(5.3), 벤더가 공개한 HEF도 손실이 크다(부록 B). 원인을 찾아 고치면 손실을 아주 작게 줄일 수 있어서 해 볼 만했다.
4. **본선 기기에서 비교할 기준이 있다.** Hailo Model Zoo에 같은 모델의 공개 HEF가 있어서 우리 결과를 벤더의 결과와 직접 비교할 수 있다.

### 3.3 Hailo-10H 호환성 사전 검토 (실칩 이식까지 완료)

예선에서 필요한 것은 DFC로 컴파일할 수 있는 구조인지 검토하는 것이지만, 우리는 예선 단계에서 실제로 HEF를 만들어 Hailo-10H 실칩에서 정확도와 지연까지 쟀다(부록 B). 본선에서는 이 HEF를 Pi 5의 HailoRT 버전에 맞춰 다시 컴파일하면 된다. HEF는 예선과 같은 모델(같은 회전 행렬과 레지스터 캐시 상수)로 만든다. CPU 제출 파일을 그대로 넣지 않고, 가중치가 비트 단위로 같은 표준 연산 FP32 파일을 Hailo 방식으로 따로 양자화한다. 그래서 5.1의 기법 중 HEF에도 적용되는 것은 그래프를 바꾸는 ④ 레지스터 캐시와 ⑤ 회전뿐이고, ①~③(ORT 양자화 설정)과 ⑥~⑧(CPU용 변환)은 들어가지 않는다.

| 항목 | 검토 결과 |
|---|---|
| 지원 연산·비표준 층 | Conv, MatMul, Add, Mul, Softmax, GELU, LayerNorm, Reshape/Transpose로 모두 DFC가 지원한다. 레지스터 캐시도 상수 곱셈·덧셈 마스크라 표준 연산이다 |
| 컴파일 / CPU Fallback | Hailo DFC 5.4.0, `--hw-arch hailo10h`로 컴파일 성공. 입력 정규화부터 출력 임베딩까지 HEF가 전부 덮어 CPU Fallback은 없다 |
| 실칩 결과 | dev 정확도 −1.55%p, 배치 1 14.93 ms, 99.9 MB. Hailo 공개 HEF보다 정확도 +2.67%p, 지연 −9.5% (test +2.73%p, 부록 B) |
| 혼합 정밀도 | 패치 경로 3개 층과 잔차 덧셈 26개만 16비트, 나머지는 8비트. Hailo 공식 설정이 16비트로 두는 층 4개(블록 0·5)도 모두 8비트로 내릴 수 있었다(부록 B) |
| INT4 | CPU에서는 4비트가 오히려 느려서 쓰지 않았다(개발 초기 모델 B/16에서 확인, 5.3). Hailo INT4는 본선에서 시험할 계획이다 |
| 버전 | 팀 DFC 5.4.0(HailoRT 5.3.0에서 실행 확인). 본선 Pi의 HailoRT 버전은 하드웨어를 받은 뒤 확인하고, 다르면 그 버전에 맞춰 다시 컴파일한다 |

본선 이식용 FP32 파일(`siglip2_image_fp32_g6b_b32_m2rot.onnx`)도 예선 제출물에 넣었다.

## 5. 적용한 최적화·양자화 기법

### 5.1 기법 요약

"단독 적용 효과"는 한 기법의 사용 여부(독립변인)만 바꾸고 나머지 조건은 같게 둔 결과다.

정확도는 고화질 5종 dev 전체 Top-1로, ①~⑤는 FP32 원본(기준) 대비 손실, ⑥~⑧은 직전 단계 대비 차이다. 지연은 직전 단계 대비 1/2/4스레드 변화율이다.

①~⑤는 i7에서 쟀고, ⑥~⑧은 285K에서 만든 ⑤ 단계 모델(dev −0.87%p)에서 이어 만들어 ⑥은 285K, ⑦⑧은 258V에서 쟀다(지연 측정 방식은 6.4와 조금 다르다).

| 적용 기법 | 적용 대상 | 주요 설정값 | 단독 적용 효과 |
|---|---|---|---|
| **기본 양자화 설정 — 모든 단계에 공통** | | | |
| ① 정적 PTQ (INT8) | 인코더 행렬곱 79개 | ORT `quantize_static`, QDQ, 가중치 채널별 INT8, 보정 256장 | ①~③만 적용하면(처방 없음) 정확도 붕괴 (−60.96%p) |
| ② Percentile 보정 | 활성값 범위 | 99.999 백분위 [9] | 코사인 유사도 0.963 (MinMax 0.931, Entropy 0.937), fc2를 FP32로 둔 상태에서 비교 |
| ③ 활성값 UINT8 + reduce_range | x86 정수 커널 | 가중치 7비트 범위 | 부호 있는 INT8 활성값보다 4스레드 약 2배 빠름 (개발 초기 모델 B/16에서 확인) |
| **정확도 복구 — 거대 활성값의 원인 처방 (5.3의 3~5)** | | | |
| ④ 레지스터 캐시 | 큰 값을 만드는 토큰 2개 | 보정 사진 평균값으로 고정, 토큰 수는 유지 | **−60.96 → −1.58%p** |
| ⑤ Hadamard 회전 | 잔차 흐름 768채널 | Hadamard 직교 회전(무작위 부호·Householder 반사), LayerNorm 흡수 | ④ 위에서 −1.58 → −0.79%p |
| **속도 개선 — ORT 정수 커널 맞춤 (5.3의 6)** | | | |
| ⑥ ORT 정수 커널 맞춤 | 행렬곱 출력, 잔차+LayerNorm | 행렬곱 출력 재반올림 생략, SkipLayerNorm 융합 | 정확도 +0.57%p, 지연 −4.9 / −8.4 / −11.4% |
| ⑦ GELU 융합 | MLP GELU 13곳 | GELU 노드 9개 → `FastGelu` 1개 | 정확도 차이 없음, 지연 −6.6 / −6.8 / −8.0% |
| ⑧ 패치 임베딩 정수화 | 패치 임베딩 Conv | INT8 행렬곱으로 바꿈, 입력은 픽셀 정수 그대로(무손실) | 정확도 차이 없음, 지연 −5.5 / −4.3 / −4.1%, 메모리 −16.2% |

①~⑧을 모두 적용한 것이 제출 모델이다(FP32 대비 전체 결과는 2장·6.5).

⑥까지 적용한 직전 모델보다 4스레드 지연은 8.8~14.4%, 메모리는 12.0~17.3% 줄었고, 정확도 차이는 없었다(x86 세 대 i7·258V·285K에서 같은 방향, dev +0.23 [−0.08, +0.53]%p는 i7).

### 5.2 양자화 상세

| 구분 | 내용 |
|---|---|
| 양자화 방식 (PTQ / QAT) | PTQ (정적 사후 양자화, 재학습 없음) |
| 정밀도 (INT8 / INT4 / 혼합) | INT8. 행렬곱 80개(패치 임베딩 1 + 인코더 79) 전부 입력·가중치 INT8. Hailo HEF는 8/16비트 혼합 |
| 캘리브레이션 데이터셋 | 고화질 5종의 train 분할에서 dev·test와 겹치지 않게 뽑은 사진 |
| 캘리브레이션 샘플 수 | 256장 (시드 0). ORT 보정기가 배치를 조용히 버린 적이 있어서, 실제로 쓰인 장수를 코드에서 확인했다 |
| 양자화 제외 레이어 | 행렬곱은 제외 없음. LayerNorm, GELU, Softmax, 잔차 덧셈은 float으로 계산 |

### 5.3 적용 근거 및 과정

**1) 단순 INT8의 실패.** 처음에 ORT 정적 양자화로 모든 연산을 INT8로 바꾸자(MinMax 보정) dev 고화질 정확도가 0.4~3.8%로 완전히 무너졌다. 행렬곱만 INT8로 하고 Percentile 보정을 써도 FP32 89.96%에서 약 29%로 떨어졌다(−60.96%p).

**2) 문제의 블록 발견** 블록 하나만 INT8로 바꾸고 나머지는 FP32로 두는 방식으로 민감도를 쟀다(그림 1). 블록 1~4는 거의 영향이 없었지만 블록 0과 5~11은 하나만 바꿔도 크게 무너졌고, 연산 유형으로는 MLP 두 번째 행렬곱(fc2)이 가장 민감했다(블록 0 안은 연산별로 나누지 않음). Hailo 공식 컴파일 설정이 16비트로 남겨 두는 층도 블록 0과 5에 몰려 있다.

![그림 1. 블록(a) 또는 연산 유형(b) 하나만 INT8로 바꿨을 때 FP32 대비 임베딩 코사인 유사도 (dev 6×200장, 고화질 5종). 주황 막대는 0.95 아래|88](F1_paper.png)

**3) 원인은 특정 토큰의 거대 활성값** 블록 5의 MLP는 사진 내용과 상관없이 늘 15번 패치 토큰의 몇몇 채널에 아주 큰 값을 썼고, 블록 9에서는 7번 토큰에서 같은 일이 생겼다. 블록 5 출력의 최댓값은 중앙값의 약 990배였다. ViT가 패치 일부를 "register"처럼 쓰는 현상[2], 거대 활성값[3]과 같은 종류로 보이며, CLS 토큰이 없는 이 모델에서도 나타났다. 활성값은 텐서마다 눈금 하나로 양자화하므로, 눈금이 이 큰 값에 맞춰 넓어지면 나머지 값은 거의 0으로 뭉개진다. 블록 5·9의 fc2를 8비트로 만들 때 그 토큰만 빼고 눈금을 정해 보니(디버깅용 fake-quant, 사진 64장) 임베딩 코사인 유사도가 0.997로 거의 돌아왔다. 8비트로도 충분했고, 문제는 눈금이었다.

**4) 원인을 직접 해결.** 두 가지를 적용했다.
- 레지스터 캐시(토큰 축)[4][5]: 문제 토큰의 값을 보정 사진에서 구한 평균 상수로 고정했다. 양자화 없이 FP32에서 이 근사를 넣었을 때 정확도 차이는 +0.06%p로 사실상 없었다.
- Hadamard 회전(채널 축)[6][7]: 잔차 흐름에 직교 행렬을 곱해 몇몇 채널에 몰린 큰 값을 768채널에 고르게 퍼뜨렸다. 역회전은 가중치에 흡수되므로 원래 모델과 수학적으로 같다.

두 기법을 적용해 보면(그림 2) 레지스터 캐시가 손실 대부분을 없앴고(−60.96 → −1.58%p), 회전은 그 위에서 손실을 절반으로 더 줄였다(→ −0.79%p). 회전만 쓰면 여전히 붕괴했다(−54.52%p). 흔히 쓰는 방식인 "문제 층만 FP32로 남기기"(−2.36%p)보다 모든 행렬곱을 INT8로 한 지금 방식이 더 정확했다.

![그림 2. 레지스터 캐시와 회전의 2×2 단독 효과 (dev 전체, 고화질 Top-1, 오차 막대 = 95% 구간). (a) 전체 범위, (b) 확대|88](F2_paper.png)

**5) 문제의 층들을 재 검토** 배포 파일과 같은 눈금으로 행렬곱 79개의 8비트 출력 SNR을 하나씩 쟀다.

| 구성 | 가장 나쁜 층 SNR (dB) | 평균 SNR (dB) | dev 손실 (%p) |
|---|---|---|---|
| 처방 없음 | 0.8 (블록 9 fc2) | 28.5 | −60.96 |
| 회전만 | 1.0 (블록 9 fc2) | 30.6 | −54.52 |
| 문제 층만 FP32 | 13.1 | 29.0 | −2.36 |
| 레지스터 캐시만 | 14.9 | 29.5 | −1.58 |
| 회전 + 레지스터 캐시 | 20.5 | 31.6 | −0.79 |

평균 SNR은 정확도 순서와 맞지 않았지만, 가장 나쁜 한 층의 SNR은 다섯 구성 모두 정확도와 순서가 같았다. 가장 나쁜 층 하나가 전체 정확도를 좌우하는 것으로 보이며, 처방 뒤 그 층의 SNR은 0.8 dB에서 20.5 dB로 올라갔다.

**6)ORT 커널 최적화를 통한 속도 향상** 정확도 문제를 해결한 뒤 프로파일을 보니 정수 행렬곱 앞뒤의 양자화·역양자화, 정수 Softmax, 합쳐지지 않은 LayerNorm에 시간이 많이 쓰이고 있었다. 그래서 행렬곱 결과를 8비트로 다시 반올림하지 않고 float으로 내도록 바꾸고, 잔차 덧셈과 LayerNorm을 하나로 합쳤다(⑥). 이 두 변경은 정확도도 조금 올렸다. 이어서 GELU를 이루던 노드 9개를 하나로 합치고(⑦), 패치 임베딩 Conv를 INT8 행렬곱으로 바꿨다(⑧). 입력 픽셀이 0~255 정수라서 눈금을 2/255로 잡으면 입력 양자화에서 오차가 생기지 않는다는 점을 이용했다.

**시도했지만 넣지 않은 것.** 판정 기준은 결과를 보기 전에 정해 두었다.

| 시도 | 결과 | 넣지 않은 이유 |
|---|---|---|
| 블록 0을 FP32로 보호 | 손실 −0.79 → −0.42%p | 개선이 통계적으로 유의하지 않은데 지연 +5.9%, 크기 +20.6% |
| 가중치 4비트 | 크기는 더 줄어듦 | x86 CPU에서 오히려 1.36~2.05배 느렸다 (개발 초기 모델에서 확인) |
| 활성값 INT8(부호 있음) | 정확도는 유의한 차이 없음 | x86에서 QKV 투영 12개와 헤드 kv 1개의 행렬곱이 정수로 합쳐지지 않아 4스레드 속도가 FP32 수준 (개발 초기 모델에서 확인) |
| ⑥의 두 변경 중 하나만 적용 | 일부 기준 미달 | 둘을 함께 적용했을 때만 기준을 모두 통과 |
| 패치 임베딩을 FP32 행렬곱으로 | 패치 출력은 Conv와 같음 | 4스레드에서 오히려 느려져(+0.2~+3.7%) 속도 기준 미달 |
| 학습 없는 가지치기(하위층 제거) | 하위층(블록 안의 attention 또는 MLP 한 덩어리) 후보 18개(24개 중 블록 0의 2개와 거대 활성값 토큰에 관련된 4개, 모두 6개는 미리 제외) 중 가장 덜 나빠지는 하나만 빼도 −10%p 이상(9번 블록의 attention −10.3, 11번 블록의 MLP −11.0, FP32 dev 6×200장). 학습 없이 뺄 수 있는 층을 찾지 못해서, 크기·지연은 INT8로만 줄였다 | 미리 정한 통과 기준(dev 손실 −0.2%p 이내)과 거리가 멀어 중단 (`results/E13-1_하위층빼기_사전확인`) |

**고려했지만 하지 않은 것.** 우리 목표는 재학습 없이 원본의 제로샷 성능을 지키는 것이라서, 학습이 필요한 지식 증류와 가지치기는 파인튜닝과 같은 이유로 범위에서 뺐다. 원본 모델을 먼저 다시 학습(파인튜닝)해 정확도를 올린 뒤 양자화하는 방법도 생각했지만 넣지 않았다. 이 대회는 원본 대비 최적화 효과를 보는 주제인데, 재학습으로 오른 정확도는 양자화 기법의 효과가 아니고 비교의 기준인 원본도 달라진다. 평가 데이터와 같은 분포로 학습하면 제로샷 평가라는 전제도 위배된다. 그래서 공개 가중치를 그대로 원본으로 두고, 재학습 없는 PTQ만 사용하였다.

### 6.2 벤치마크 선정 사유 및 타당성

- 분야가 다른 세밀 분류 5종(동물, 꽃, 자동차, 음식, 일반 사물)을 평균해 한 분야에만 맞춘 결과를 피했다. 비슷한 클래스를 구분해야 해서 작은 임베딩 오차도 정확도에 드러난다.
- 프롬프트는 CLIP 논문의 공식 템플릿[8]을 썼다. SigLIP 권장 템플릿과 dev에서 비교하면 CLIP 템플릿이 1.77%p 높았다.
- CIFAR-100과 ImageNetV2는 보조 지표로 따로 적었다. CIFAR-100은 32×32 사진을 키운 것이라 앞쪽 층 변화에 지나치게 민감해서 설정 선택에는 쓰지 않았고, ImageNetV2는 일반 사진에서도 괜찮은지 보는 용도다.
- ImageNet-1k 검증셋은 등록이 필요해 ImageNetV2를 썼고, 이미지-텍스트 검색(텍스트 인코더 영향이 섞임)과 linear probe(추가 학습 필요)는 뺐다.

보정은 train 사진으로, 설정 선택은 train에서 떼어 낸 dev로만 했다. B/32 모델로 ORT에서 test 분할을 쓴 것은 두 번이다. 처음은 당시 최종 후보였던 직전 모델(⑥까지 적용)이었고, 두 번째는 제출 모델을 dev 정확도·지연·메모리 기준(결과 전에 고정)으로 고른 뒤였다. 두 번 모두 평가할 파일을 sha256으로 고정했고(두 번째는 판정 기준도 미리 커밋), test 결과를 보고 설정을 바꾸지 않았다. 직전 모델의 test 손실(−0.23%p)은 제출 모델(−0.20%p)과 차이가 없었다. Hailo test는 한 번, 개발 초기 모델(B/16)에서는 후보 두 개로 한 번씩 썼고, B/32로 바꾼 결정은 dev와 실칩 dev만 보고 했다.

통계는 같은 사진끼리 짝지은 부트스트랩(1,000회)으로 95% 신뢰구간을 내고, 구간이 0을 포함하지 않으면 유의한 차이로 봤다. 보정 사진의 시드를 바꿔도 dev 손실은 −0.79 / −0.80 / −0.70%p로 거의 같았다(회전+레지스터 캐시 단계). 사진을 뒤집거나 흑백으로 바꾸는 등 입력 변형 8종에서는 90도 회전에서만 작지만 유의한 손실(−1.5%p)이 있었다.

### 6.3 재현 가능성 확보 방안

- 데이터셋은 모두 공개 데이터이고 실행하면 자동으로 받는다(ImageNetV2만 9.2 (다)의 명령으로). dev 사진은 고화질 5종은 이미지 해시로, CIFAR-100은 고정 구간으로 정해 누가 돌려도 같다.
- **소규모 평가 묶음**: dev 6종 × 200장(전처리한 입력, 정답, FP32 텍스트 분류기)과 numpy·onnxruntime만 쓰는 `portable_eval.py`를 Release에 넣어, 전체 데이터 없이 몇 분 만에 FP32와 제출 모델을 비교할 수 있다(9.2 (가)).
- 모델 파일은 sha256과 함께 공개했다(FP32 `be19a8ad…`, 제출 모델 `e465d10d…`). 같은 PC의 빈 폴더에 Release만 받아 실행해 보니 사진별 예측까지 기준 결과와 비트 단위로 같았다.
- 기준 PC(i7)에서 이 묶음의 결과는 FP32 고화질 88.9%, 제출 모델은 이보다 +0.4%p, 코사인 유사도 0.9884였다. 다른 CPU(Core Ultra 9 285K, Jetson AGX Orin)에서는 FP32는 같았고, 제출 모델은 x86끼리 1장, ARM과 4~5장(0.3~0.4%)이 달랐다(정수 커널의 반올림 차이로 보임). 비교용으로 i7의 사진별 예측도 Release에 넣었다.
- 채점에는 Release의 ONNX 파일을 써야 결과가 같다. 처음부터 다시 만들면 PC마다 회전 행렬이 조금 달라져서 결과가 0.1%p 안팎 달라진다(같은 방법으로 두 PC에서 만든 B/32 모델의 dev 손실 −0.79, −0.87%p).

| 배치 크기 | 1 (엣지에서 사진 한 장씩 처리하는 상황). 정확도 평가만 배치 50 |
| Warm-up 횟수 | 모델마다 20회 |
| 측정 반복 횟수 | 사진 200장 × 3회를 FP32와 최적화 모델이 번갈아 실행, 이것을 세션 3번 × 스레드 1·2·4로 반복 |
| 통계 방식 (평균 / p50 / p95) | 세션마다 장당 평균을 구하고 세션 중앙값을 대표값으로 씀. p50·p95도 기록 |
| 측정 도구 및 방법 | ONNX Runtime 1.25.0 CPU, `ORT_ENABLE_ALL`, 스레드 수 고정, `siglip2/scripts/cross_latency.py --no-mem-pattern`. 피크 메모리는 모델마다 새 프로세스에서 세션 생성과 추론 50회 중 최대 사용량 |

모델을 하나씩 따로 재면 같은 모델도 잴 때마다 결과가 크게 달랐다(노트북 CPU 클럭 변화 탓으로 보인다). 그래서 FP32와 최적화 모델을 같은 실행 안에서 번갈아 돌려 비율로 비교했다. 대표값은 두 번의 실행(세션 6개)을 합친 비율의 중앙값이고, 이 규칙은 두 번째 실행 전에 커밋해 두었다.

채점은 팀이 낸 실행 스크립트로 하므로, 제출 스크립트와 FP32 측정 모두에 메모리를 아끼는 옵션(`enable_mem_pattern=False`)을 넣었다. 이 옵션은 출력을 바꾸지 않고(사진 1,200장이 비트 단위로 같음) 지연과 메모리에 주는 영향도 작다(지연 −1.6~+0.5%는 개발 초기 모델 값, 메모리는 다른 실행끼리 비교해 제출 모델 −2.2%·직전 모델 변화 없음). 이 설정을 기준으로 삼기로 한 것은 옵션 없이 잰 값(4스레드 −59.8%, 1스레드 −67.6%, 메모리 −62.6%)을 본 뒤였지만, 두 값의 차이는 실행마다 생기는 흔들림 범위(−58~−65%) 안이다.

### 6.6 결과 해석

- 큰 손실의 원인이던 거대 활성값은 레지스터 캐시와 회전으로 없앴다(가장 나쁜 층 SNR 0.8 → 20.5 dB). 남은 손실은 행렬곱을 전부 8비트로 바꾸면서 생기는 작은 임베딩 오차(코사인 유사도 0.988)다.
- 회전+레지스터 캐시 단계 모델로 dev에서 새로 틀린 사진을 보면, 새로 틀린 사진은 특정 클래스에 몰리지 않고 대부분 클래스마다 1~2장씩 흩어져 있었다. 원래도 헷갈리는 쌍(스태퍼드셔 불 테리어와 아메리칸 핏불 테리어, 랙돌과 버먼 고양이 등)에서 답이 뒤집히는 경우가 많았다.
- 데이터셋별로는 세밀한 구분이 필요한 Cars(−0.45%p)와 Flowers(−0.39%p)에서 작지만 유의한 손실이 있었고, Pets·Food·Caltech는 거의 그대로였다. 저해상도인 CIFAR-100은 오히려 0.57%p 올랐지만 유의하지 않았고 원인도 찾지 못했다. 일반 사진인 ImageNetV2는 −0.43%p로 작지만 유의한 손실이 있었다.
- 입력 변형 8종 중에서는 90도 회전에서만 작지만 유의한 손실(−1.5%p)이 있었다(6.2). 원본 FP32도 회전한 사진에서는 정확도가 크게 떨어지는 학습 분포 밖 입력이라, 회전된 사진이 많은 쓰임새라면 따로 확인이 필요하다.
- dev(−0.05%p)와 test(−0.20%p)가 비슷해서, dev로 설정을 고르며 생길 수 있는 과적합은 보이지 않았다. test는 사진이 많아 구간이 좁아서 작지만 유의한 손실로 나왔다.
- i7 4스레드 프로파일에서 제출 모델은 직전 모델보다 커널 시간이 15% 줄었다(34.9 → 29.5 ms). 줄어든 곳은 GELU와 FP32 패치 Conv였고 정수 행렬곱 시간은 그대로여서, 지금은 커널 시간의 절반 이상(53%)이 정수 행렬곱이다. 처리량 기준 배속은 1스레드 3.2배, 2·4스레드 약 2.8배였다.

## 7. 한계점 및 엣지 디바이스 이식 계획

### 7.1 현재 한계점

1. **제출 모델의 FP32 대비 대표값은 i7 노트북 한 대에서 쟀다.** 285K에서는 직전 모델의 FP32 대비 개선율을, 285K와 258V에서는 제출 모델이 직전 모델보다 빨라진 정도를 쟀고 모두 같은 방향이었지만(6.5), 제출 모델을 FP32와 직접 번갈아 잰 것은 i7뿐이다. i7에서도 FP32 절대 지연이 실행에 따라 최대 약 48%까지 달라서(연속 실행으로 발열된 실행 포함) 같은 실행 안의 비율로만 비교했고, 비율도 세션마다 −58~−65%로 흔들렸다. 전원 모드도 결과를 크게 바꿔서 측정 전에 확인했다.
2. **제출 모델은 onnxruntime에서만 돈다**(전용 연산 SkipLayerNormalization·FastGelu). 비상 대체용으로 표준 연산만 쓰는 INT8 모델(dev −0.87%p)도 Release에 두었다.
3. **CPU 종류에 따라 사진 몇 장의 결과가 다를 수 있다**(6.3). VNNI 명령어가 없는 x86 CPU에서는 확인하지 못했다.
4. **Hailo에서는 CPU보다 손실이 크다.** test 손실이 CPU는 0.20%p, Hailo는 1.04%p였다. Hailo는 같은 FP32 모델을 자기 방식(8/16비트 혼합, DFC 보정)으로 따로 양자화하기 때문으로 보인다. 두 값의 FP32 기준도 정의가 조금 다르다(부록 B).
5. **레지스터 캐시는 보정 사진으로 정한 근사값이다.** FP32에서 이 근사만 넣었을 때 dev 전체와 입력 변형 8종에서 정확도 차이가 없었고(입력 변형에서 코사인 유사도 0.9997 이상), train에서 따로 뗀 확인용 1,200장은 코사인 유사도만 쟀다(평균 0.99986, 가장 낮은 사진 0.9908). test 데이터셋이나 분포가 아주 다른 사진에서는 따로 재지 않았다.

## 9. 재현 실행 절차

### 9.1 환경 구성

명령은 bash 기준이다(Linux·macOS, Windows는 Git Bash·WSL, Python 3.11). 9.2 (가)는 PowerShell 명령도 있다.

```bash
git clone https://github.com/jungminmobile/oslab_mobile.git
cd oslab_mobile
git checkout prelim-submit
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
python -m pip install -r siglip2/requirements.txt \
  --extra-index-url https://download.pytorch.org/whl/cpu
gh release download siglip2-b32-p2-submit-20261027 \
  --repo jungminmobile/oslab_mobile -D release
cd release && sha256sum -c SHA256SUMS.txt && cd ..
export S2_MODEL_ID=hf-hub:timm/ViT-B-32-SigLIP2-256
export SIGLIP2_DATA=$HOME/siglip2_data
export SIGLIP2_ARTIFACTS=$HOME/siglip2_b32_art
export HF_HOME=$HOME/hf_cache
export OPENBLAS_NUM_THREADS=1
mkdir -p $SIGLIP2_ARTIFACTS/onnx
cp release/*.onnx $SIGLIP2_ARTIFACTS/onnx/
```
- `gh`가 없으면 브라우저로 Release 페이지(https://github.com/jungminmobile/oslab_mobile/releases/tag/siglip2-b32-p2-submit-20261027)에서 받아 `release/` 폴더 하나에 둬도 된다. 빠른 확인(9.2 (가))만 할 때는 저장소를 받지 않아도 된다.
- Windows PowerShell에서는 `export` 대신 `$env:S2_MODEL_ID="..."`처럼 쓴다.

### 9.4 재현 시 유의사항

1. 채점에는 Release의 ONNX 파일과 onnxruntime 1.25.0을 쓴다(제출 모델에 onnxruntime 전용 연산이 있음, 7.1).

## 부록 B. Hailo-10H 실칩 이식 (예선에서 미리 수행)

본선 NPU인 Hailo-10H를 NVIDIA Jetson AGX Orin에 연결해(HailoRT 5.3.0, DFC 5.4.0) 예선 모델을 미리 컴파일했다. CPU에서 찾은 처방이 벤더 툴체인의 양자화에서도 통하는지, Hailo가 공개한 같은 모델의 HEF보다 나은 HEF를 만들 수 있는지를 보려는 것이다. 개발 초기 모델에서 에뮬레이터는 정상인데 실칩에서만 정확도가 무너진 경우(top-1 50.68%)가 있어서 정확도는 모두 실칩에서 쟀다.

### B.1 결과 (dev 전체 5,923장, 실칩)

| HEF | dev 정확도 (FP32 대비, %p) | 공개 HEF 대비 (%p) | 배치 1 지연 | 크기 |
|---|---|---|---|---|
| Hailo Model Zoo 공개 HEF | −4.22 [−4.95, −3.45] | — | 16.49 ms | 102.6 MB |
| **우리 HEF (본선용)**¹ | **−1.55 [−2.09, −1.03]** | **+2.67 [+1.92, +3.46]** | **14.93 ms (−9.5%)** | 99.9 MB |
| 잔차·패치 경로까지 8비트 (비교 실험) | −2.42 [−3.04, −1.77] | +1.80 [+1.05, +2.63] | 13.38 ms (−18.9%) | 91.8 MB |

¹ 16비트로 남긴 것은 패치 경로 3개 층과 잔차 덧셈 26개뿐이다. dev 값은 컴파일 설정 두 줄(B.2의 ⑤)을 넣기 전 구성에서 쟀고, 두 HEF의 출력은 사진 1,200장에서 비트 단위로 같았다. 세 HEF의 지연은 같은 세션에서 쟀다. 우리 HEF 크기는 바탕 FP32 ONNX보다 73.6% 작다(Hailo에는 FP32 실행 경로가 없어 지연은 FP32와 비교하지 않았다).

### B.2 정확도 이득은 어디서 왔나

공개 HEF의 레시피(Hailo Model Zoo v5.4.0)에서 출발해 하나씩 바꾸면서 실칩 dev 정확도를 쟀다.

| 단계 | 바꾼 것 | 공개 HEF 대비 정확도 (%p) | 공개 HEF 대비 지연² |
|---|---|---|---|
| ① | 같은 레시피에 회전만 넣음 | +0.65 [−0.19, +1.46] (차이 없음) | +1.5% |
| ② | ①에 레지스터 캐시를 더함 | +2.12 [+1.37, +2.89] | ①보다 +1.63 ms |
| ③ | 최적화 수준 0→1, 보정 사진 64→256장 | +3.17 [+2.41, +3.95] | +11.4% |
| ④ | 16비트 보호층을 공개 레시피보다 줄임(블록 0·5의 4개 층도 8비트) | +2.67 [+1.92, +3.46] | −5.2% |
| ⑤ | Zoo의 다른 CLIP 레시피(ViT-B/16)에서 컴파일 설정 두 줄을 가져옴 = 본선 HEF | +2.67 (④와 출력 같음) | −9.5% |

² ①~③과 ④⑤는 서로 다른 측정 세션이고, 각 세션에서 같이 잰 공개 HEF와 비교했다.

CPU에서 회전만으로는 붕괴를 막지 못했듯이, Hailo에서도 회전만으로는 공개 HEF와 유의한 차이가 없었고, 이득의 가장 큰 몫(①→② +1.48%p)은 레지스터 캐시에서 나왔다. 최적화 수준과 보정 장수가 +1.05%p를 더했다. 레지스터 캐시가 늘린 지연(1.63 ms)은 ④(16비트 층 축소)와 ⑤(컴파일 설정 두 줄, 출력은 그대로 −0.70 ms)로 상쇄되어, 본선 HEF는 공개 HEF보다 9.5% 빨라졌다. ⑤는 벤더 설정이라 우리 기법으로 치지 않는다. ④는 공개 레시피가 16비트로 지키는 층까지 8비트로 내렸는데도 공개 HEF보다 여전히 2.67%p 정확했다(③보다는 0.50%p 낮음, 처방 없는 모델로 같은 대조는 하지 않음).

### B.3 test (1회, 실칩)

HEF는 test 전에 고정했다. Hailo 쪽 FP32 기준(Zoo 전처리를 쓴 PyTorch 모델)은 CPU 쪽과 정의가 다르지만 고화질 평균은 둘 다 88.51%다.

| 데이터셋 | FP32 | 우리 HEF | 공개 HEF | 우리 − 공개 (%p) | 우리 − FP32 (%p) |
|---|---|---|---|---|---|
| **고화질 5종 평균** | 88.51 | 87.47 | 84.75 | **+2.73 [+2.46, +3.02]** | −1.04 [−1.24, −0.85] |
| (보조) CIFAR-100 | 76.05 | 72.18 | 70.98 | +1.20 [+0.48, +1.95] | −3.87 [−4.50, −3.18] |
| (보조) ImageNetV2 | 65.85 | 63.84 | 60.76 | +3.08 [+2.39, +3.77] | −2.01 [−2.57, −1.50] |

dev와 같은 크기로 공개 HEF를 앞섰지만, FP32 대비 손실은 CPU 제출 모델(−0.20%p)보다 크고 CIFAR-100에서 가장 커서 본선에서 줄일 과제다. 잔차·패치 경로까지 8비트로 내리면 본선 HEF보다 지연은 10.4% 더 줄지만(공개 HEF 대비 −18.9%) dev 정확도가 0.87%p 더 떨어져서, 본선 HEF는 잔차를 16비트로 남겼다.
