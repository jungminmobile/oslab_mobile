**요약.**
- 이미지-텍스트 대조 학습 모델 **SigLIP2 B/32의 이미지 인코더**를 재학습 없는 **INT8 정적 사후 양자화(PTQ)**로 최적화했다. 단순 INT8은 정확도가 무너졌다(dev −61.0%p).
- 원인(고정 위치 토큰 2개의 거대 활성값)을 찾아 **레지스터 캐시(토큰 축) + Hadamard 회전(채널 축)**으로 고쳤고, ORT 커널에 맞춘 **O-A(행렬곱 출력 재반올림 생략)·O-B(SkipLayerNorm 융합)·GELU 융합·패치 임베딩 정수화**를 더했다. 패치 임베딩을 포함한 행렬곱 80개를 **예외 없이 모두 INT8**로 했다.
- 결과: 크기 −74.7%, CPU 지연 4스레드 −62.9%·1스레드 −68.0%(실행별 4스레드 −59.8~−64.4%), 메모리 −63.4%, test 정확도 −0.20%p. 배포 파일 눈금으로 잰 "가장 나쁜 층"의 SNR 순서가 정확도 순서와 같아, 원인과 처방을 층 단위로 확인했다(5.3).
- 본선 기기 Hailo-10H 실칩에서도 같은 모델로 만든 HEF가 Hailo Model Zoo 공개 HEF보다 지연 −9.5%, test 정확도 +2.73%p였다(FP32 대비 test −1.04%p, 부록 F).

## 3. 대상 모델 및 선정 사유

### 3.1 대상 모델

| 구분 | 내용 |
|---|---|
| 모델명 / 버전 | SigLIP2 ViT-B/32, 입력 256×256 (`hf-hub:timm/ViT-B-32-SigLIP2-256`, open_clip 3.3.0 / timm 1.0.30) |
| 모델 유형 | 멀티모달(이미지-텍스트 대조 학습). 최적화 대상은 **이미지 인코더** |
| 저장소 URL | 우리 코드: https://github.com/jungminmobile/oslab_mobile [확인 필요: 현재 비공개 — 학술부 접근 방법] / 원 모델: https://huggingface.co/timm/ViT-B-32-SigLIP2-256 |
| 커밋 해시 또는 릴리스 태그 | 제출 시점 main의 `prelim-submit` 태그 [확인 필요: 태그·커밋]. 모델 파일 Release `siglip2-b32-p2-submit-20261027` (지금은 내부 확인용 pre-release, 제출 때 정식 Release로 바꾼다) |
| 사전학습 가중치 출처 | Google SigLIP2 (Tschannen et al., 2025) 공개 가중치의 timm/open_clip 변환본 (Hugging Face, 로컬 캐시 스냅샷 `cd1efb47…`) |
| 라이선스 | [확인 필요: 모델 카드 라이선스, Apache-2.0로 알고 있음] |

- 구조: 패치 32×32 → 토큰 64개(8×8), 폭 768, 블록 12개, GELU(tanh 근사). CLS 토큰 없이 attention pooling(MAP) 헤드로 768차원 임베딩을 낸다.
- 파라미터 94,552,320개(PyTorch = ONNX), 5.75 GMACs = **11.50 GFLOPs**(fvcore), FP32 ONNX 360.83 MiB.
- **범위**: 이미지 인코더만 양자화한다. 텍스트 쪽 클래스 임베딩은 FP32로 한 번 계산해 다시 쓴다. 기기에서 사진마다 도는 것은 이미지 인코더뿐이다.

### 3.2 선정 사유

1. **엣지 쓰임새가 넓다.** 임베딩 하나로 제로샷 분류·검색·필터링을 하고, 클래스가 바뀌어도 재학습 없이 텍스트만 바꾼다.
2. **최신이고 최적화 가치가 크다.** SigLIP2(2025)는 CLIP 계열 최신판이고, FP32 이미지 인코더가 378 MB, 노트북 1스레드 한 장 약 127 ms다.
3. **원본 대비 개선 여지가 크다.** 단순 INT8은 붕괴(dev −61.0%p)하지만 원인을 고치면 패치 임베딩을 포함한 행렬곱 80개를 모두 INT8로 해도 손실이 작다(5장). 모델 크기 −74.7%, 4스레드 지연 약 −63%.
4. **본선 기기(Hailo-10H)에서 벤더 공개 기준과 직접 비교할 수 있다.** Hailo Model Zoo에 SigLIP2 B/32 공개 HEF가 있다. 예선·본선은 같은 모델을 쓴다(대회 원문 2·5.2절).

### 3.3 Hailo-10H 호환성 사전 검토

본선 HEF는 예선 ONNX와 **같은 PyTorch 모델**(회전 행렬 `3a6391a2…`, sink 규칙 `15@6:5, 7@10:9`, 같은 레지스터 캐시 상수)을 배치 1로 export한 FP32(`a0eb502b…`)를 Hailo DFC로 따로 양자화·컴파일한다. 예선 ONNX는 같은 모델의 배치 가변 FP32(`23236123…`)에 O-B를 더해 양자화했다. 두 FP32는 initializer 145개가 비트 단위로 같고 배치 축 모양 계산만 다르며, PyTorch 대비 cos 최소 0.99999999697이다(준용 `B32_hef_test` A절). O-A·O-B는 ORT CPU용이라 HEF에는 없다(7.1).

| 항목 | 검토 결과 |
|---|---|
| 지원 연산 | Conv(패치 임베딩), MatMul, Add, Mul, Softmax, GELU(tanh), LayerNorm, Reshape/Transpose. 모두 DFC 지원(LayerNorm은 DFC가 분해) |
| 비표준 층 | 모델(FP32 그래프)에는 없다. 레지스터 캐시는 상수 Mul·Add 마스크로 토큰 수를 유지해 표준 연산으로 컴파일된다(토큰 삭제형은 LayerNorm 분해와 충돌해 안 씀). 제출 ONNX의 com.microsoft 연산(SkipLayerNorm·FastGelu)은 CPU 배포용 마지막 단계에서만 쓰고, HEF는 표준 연산 FP32에서 컴파일한다 |
| 실제 컴파일 | Hailo DFC 5.4.0, `--hw-arch hailo10h`로 HEF 컴파일 성공(여러 구성, 부록 F.2). 입력은 UINT8 픽셀(NHWC) 그대로, **정규화도 HEF 안**, 출력 768차원(UINT16) |
| CPU Fallback | 없음. HEF의 끝 노드가 ONNX의 마지막 노드(출력 `embedding`)라 HEF가 그래프 전체를 덮는다(`B32_hef_test` A-1). 후처리 연산이 없고, 정규화도 HEF 안이다 |
| 혼합 정밀도 | 본선 HEF(GF): 패치 경로(`norm1`·`conv1`·`format_conversion1`)와 잔차 덧셈 26개만 16비트(a16_w16), 나머지 8비트(a8_w8). Zoo 공식 설정이 16비트로 두는 블록 0의 어텐션 출력 투영·fc1·fc2와 블록 5 fc2(`conv3·4·5·25`)도 8비트로 내렸다(회전·레지스터 캐시로 거대 활성값을 없앤 그래프에서 시험했고, 처방 없는 그래프로는 시험하지 않음). 컴파일 자원 설정은 Hailo Model Zoo v5.4.0 레시피에서 가져왔다(부록 F.1) |
| 실칩 확인 | 부록 F (학술부 답: NPU에서 직접 실행한 결과도 보고서에 넣어도 됨) |
| 본선 이식용 바탕 | 예선 제출물에 같은 모델의 표준 연산 FP32 `siglip2_image_fp32_g6b_b32_m2rot.onnx`(`23236123…`)를 함께 낸다. 제출 P2는 이 그래프를 CPU용으로 양자화·변환한 파일이다. 이 FP32 바탕(`23236123…`)과 본선 HEF 바탕(`a0eb502b…`)은 initializer 145개가 비트 단위로 같다 |
| INT4 | Hailo-10H는 INT4 지원. CPU에서는 4비트가 느려 넣지 않았다(5.3). Hailo INT4는 본선에서 시험한다 |
| 버전 위험 | 팀 DFC 5.4.0, 본선 Pi의 HailoRT는 [확인 필요: 주최측]. 버전이 다르면 그 버전용 DFC로 다시 컴파일한다 |

- 본선 HEF는 GF(위 혼합 정밀도 + Zoo 컴파일 설정, `0c2e04a6…`)로 정했다(D-050). 16비트 보호를 모두 걷어낸 ALL8F는 절제 실험이다(부록 F).

### 5.1 기법 요약

### 5.3 적용 근거 및 과정

판정 기준은 결과를 보기 전에 정해 기록했다(`siglip2/DECISIONS.md`, 결과 폴더 README). 개발 초기 모델(SigLIP2 B/16)에서 먼저 찾은 원인·처방을, 제출 모델 B/32에서 처음부터 같은 순서로 다시 진단했다(부록 D).

**단계 1. 단순 INT8은 무너진다.** MinMax·모든 연산 INT8이면 고화질 Top-1 0.4~3.8%(cos 0.38~0.42), MatMul만·Percentile이어도 −60.96%p다.

**단계 2. 민감도 지도** (블록 하나만 INT8, 나머지 FP32, dev 6×200, 고화질 cos, 그림 F1)

| 블록 | 0 | 1~4 | 5 | 6 | 7 | 8 | 9 | 10 | 11 |
|---|---|---|---|---|---|---|---|---|---|
| cos | **0.521** | 0.986~0.997 | **0.519** | **0.475** | **0.470** | **0.495** | **0.551** | **0.620** | **0.722** |

<!-- src: b32/README.md B4 -->
- 블록 5부터 무너지고, 연산별로는 **MLP fc2만 붕괴**(0.620), QKV·attention은 둔감(≥ 0.997). **블록 0도 민감**하다(0.521, 아래 실패 표).
- 벤더도 같은 층을 지킨다: Hailo Model Zoo의 B/32 컴파일 설정(`.alls`)이 16비트로 두는 층은 블록 0의 어텐션 출력 투영·fc1·fc2와 블록 5 fc2다. 우리 민감도 지도에서 가장 먼저 무너지는 블록(0과 5)과 겹친다(블록 6~11은 Zoo도 지키지 않는다).

**단계 3. 원인: 고정 위치 토큰의 거대 활성값(attention sink).**
- 블록 5 MLP가 사진과 상관없이 **패치 15번 토큰**(채널 67·301·145)에, 블록 9 MLP가 **패치 7번 토큰**(채널 483)에 아주 큰 값을 쓴다. 블록 5 출력 최댓값이 중앙값의 약 990배다(128장).
- 15번은 128장 모두, 7번은 95%에서 고정 위치이고, 블록 6~11에서 attention의 26~48%가 15번에 몰린다(균등이면 1.6%). CLS 없는 ViT가 패치를 "register"처럼 쓰는 현상이다 [3][4].
- 텐서당 눈금 하나(per-tensor) 8비트에서 이 값이 눈금을 넓혀 층 출력이 망가진다(배포 눈금 SNR **블록 9 fc2 0.8 dB**, 신호와 오차가 거의 같음). fake-quant(64장)로 거대 값 토큰만 빼고 눈금을 정하면 cos 0.997, 토큰별 눈금 0.999, 채널별 1.000 → **"8비트가 부족한 것이 아니라 눈금 단위가 맞지 않는 것"**이다.

**단계 4. 원인을 직접 고친다.**
- **토큰 축 — 레지스터 캐시(M2)** [5][6]: sink 토큰의 K·V를 보정 평균 상수로, 그 행의 MLP 입력을 평범한 값(u_c)으로 바꾼다. 규칙 `15@6:5, 7@10:9` = K·V는 블록 6·10부터, MLP 입력은 5·9부터(15번 K·V를 블록 5부터 바꾸면 FP32 cos 0.998, 한 블록 늦추면 0.9998). 양자화 없이 dev 전체 **+0.06 [−0.04, +0.19], cos 0.9999** — 근사 손실이 없다.
- **채널 축 — 오프라인 회전** [7][8]: 잔차 흐름을 직교 행렬로 돌리고 역회전을 가중치에 흡수, LayerNorm γ·β를 접어 원래 모델과 수학적으로 같다. 몇 채널의 큰 값이 768채널로 퍼진다.
- **2×2 결과**(그림 F2): M2가 결정적(−60.96 → −1.58), 회전은 M2 위에서 유의하게 더한다(→ −0.79), 회전만은 붕괴(−54.52). 예전 방식(블록 5·9 fc2 FP32, −2.36)보다 **MatMul 79개 전부 INT8**이 더 정확하다(+1.57 [+0.98, +2.23]).

**단계 5. 무엇이 정확도를 정하나 — 배포 눈금의 층별 SNR.** 배포 파일과 같은 눈금·정수 가중치(출력 재반올림 포함)로 MatMul 79개 각각의 8비트 출력 SNR을 쟀다(사진 64장, 층마다 FP32 입력에서 시작, 그림 F4b).

| 그래프 | 최솟값 dB (가장 나쁜 층) | 평균 dB | dev 손실 %p |
|---|---|---|---|
| 원래 | 0.8 (블록 9 fc2) | 28.5 | −60.96 |
| 회전만 | 1.0 (블록 9 fc2) | 30.6 | −54.52 |
| 예전 방식(블록 5·9 fc2 FP32) | 13.1 | 29.0 | −2.36 |
| M2만 | 14.9 | 29.5 | −1.58 |
| **회전 + M2** | **20.5** | **31.6** | **−0.79** |

<!-- src: b32/submit_prep/H5_qdq_snr/why_after_qdq_summary.json ("full") -->

- **가장 나쁜 층의 SNR 순서가 정확도 순서와 5개 모두 같다.** 평균은 맞지 않는다(회전만 30.6 dB > M2만 29.5 dB인데 붕괴). 가장 나쁜 한 층이 전체 정확도를 좌우하는 것으로 보이며, 처방은 그 층의 SNR을 올린다(0.8 → 20.5 dB).

**단계 6. ORT 커널에 맞추기(O-A·O-B, 준용 O1).** 남은 비용은 정수 행렬곱 앞뒤 Q/DQ, 정수 Softmax, 합쳐지지 않은 LayerNorm이었다.
- O-A: 정수 행렬곱 결과를 8비트로 다시 반올림하지 않고 float으로 낸다(ORT 최적화 뒤 독립 DQ 66 → 1개). FP32 대비 cos가 0.977 → 0.989로 올랐다. 출력 재반올림과 정수 Softmax가 없어진 효과로 보이지만, 두 원인을 나누지는 않았다.
- O-B: 소비자가 둘이라 기본 융합이 안 되던 잔차 Add + LayerNorm을 `SkipLayerNormalization`으로 합쳤다(FP32에서 수학적으로 같음).
- 같은 바탕 비교에서 O-AB가 +0.57 [+0.17, +0.97], 4스레드 −11.4%로 사전 기준 세 개를 모두 만족했다.

**단계 7. 남은 float 연산 줄이기(정민 E14).** O-AB 프로파일에서 남은 float 비용은 GELU를 이루던 Mul·Add와 FP32 패치 임베딩 Conv였다.
- F2: GELU(tanh) 노드 9개와 bias Add를 `FastGelu` 하나로 합쳤다.
- P2: 패치 임베딩 Conv를 자르기 + INT8 MatMul로 바꿨다. 입력은 0~255 픽셀 정수를 /127.5 − 1 한 값이라, `x + 1`을 눈금 2/255로 양자화하면 픽셀 정수가 그대로 나온다(무손실). 오차는 가중치 INT8에서만 생긴다(패치 출력 cos 0.99993).
- 이 PC 기본 세션 같은 실행에서 P2는 O-AB보다 지연 −8.8~−11.8%, 메모리 −12.0%, dev +0.23 [−0.08, +0.53](동률)로, 결과 전에 정한 기준 세 개를 만족해 제출 파일로 정했다(D-052). 프로파일에서 줄어든 곳은 GELU의 Mul·Add와 FP32 Conv이고, 정수 행렬곱 시간은 같다(`latency_this_pc/b32_p2_20261027`).

**시도했지만 넣지 않은 것** (결과 전에 정한 기준으로 판정)

| 시도 | 결과 | 넣지 않은 이유 |
|---|---|---|
| 블록 0 FP32 보호 (X3) | −0.79 → −0.42, cos 0.977 → 0.991 | 짝 차이 +0.37 [−0.07, +0.80] 동률, 4스레드 지연 +5.9%, 크기 +20.6% → 사전 기준 두 개 미달 |

### 6.2 벤치마크 선정 사유 및 타당성

- **분야가 다른 세밀 분류 5종 평균**(동물·꽃·자동차·음식·일반 사물): 비슷한 클래스를 구분해야 해 작은 임베딩 오차도 정확도에 드러난다.
- **프롬프트는 CLIP 공식 템플릿 [2]**: SigLIP 권장 템플릿보다 dev에서 1.77%p 좋았다(SigLIP 템플릿 − CLIP 템플릿 = −1.77 [−2.33, −1.22]).
- **보조 지표는 따로 적는다**: CIFAR-100은 32×32를 키운 사진이라 앞쪽 층 변화에 지나치게 민감해 설정 선택에 쓰지 않는다. ImageNetV2는 일반성 확인용이다.
- **고르지 않은 대안**: ImageNet-1k 검증셋(등록제라 재현이 어려움 → 공개 ImageNetV2), 이미지-텍스트 검색(텍스트 인코더 효과가 섞임), linear probe(학습 필요, 쓰임새와 다름).
- **데이터 구간 분리**: 사진 선택은 이미지 바이트 SHA-1 해시로 정해 누가 돌려도 같다. 보정·구성 선택은 train(dev)에서만 했다. **test는 구성 선택에 쓰지 않았다. 제출 모델 B/32로는 ORT 2회(10/22 이전 제출 파일 O-AB, 10/27 교체한 P2), Hailo 본선 HEF(GF와 비교용 Zoo HEF) 1회를 썼다.** ORT는 제출 파일(D-049, D-052)을, Hailo는 판정 기준·HEF 선택을 test 전에 커밋해 고정했다. P2로의 교체는 dev와 지연·메모리만 보고 test 전에 확정했고, P2 test 결과로 되돌리지 않기로 미리 정했다. B/32 결정과 설계는 dev(실칩 dev 포함)만으로 했다. 개발 초기 모델의 test 이력은 부록 E에 적는다.
- **결과 전 고정과 검토**: 판정 기준·주 조건(4스레드)·HEF 선택은 결과를 보기 전에 결과 폴더 README에 적어 커밋했다(O-A·O-B 기준표는 평가 시작 38초 뒤, 결과를 보기 전에 커밋). 결과마다 자기 검증 → 다른 경로 재계산 → 맥락을 모르는 검토자 확인의 3단계를 거쳤고, 검토 뒤 바꾼 분석은 "사후 변경"으로 표시했다(`siglip2/VERIFICATION.md`).
- **통계**: 같은 사진끼리 짝지은 부트스트랩(데이터셋별 층화, 1,000회, 시드 0)으로 95% 구간을 냈다. 구간이 0을 포함하지 않으면 "유의"로 본다.
- **흔들림 점검**: 보정 시드 0·1·2(M2rot, 이 PC) −0.79 / −0.80 / −0.70(폭 0.10, 시드끼리 짝 차이 모두 유의하지 않음). 같은 레시피를 준용 PC에서 만들면 −0.87(이 PC −0.79). 입력 변형 8종(변형 없음·좌우 반전·90도 회전·흑백·어둡게·저대비·잡음·JPEG 20, 고화질 5종 × 200장, 같은 변형의 FP32 대비)에서 **제출 P2는 90도 회전만 작지만 유의한 손실(−1.5 [−2.8, −0.1]), 나머지 7종은 유의한 손실 없음(−0.6 ~ +0.8%p)**. 같은 실행의 이전 단계 O-AB는 8종 모두 유의하지 않았다(−0.9 ~ +0.6). M2 근사는 모든 변형에서 cos 0.9998 이상. 비교로 M2rot INT8은 흑백 −3.5·90도 회전 −2.2, 예전 방식은 흑백 −9.0으로 유의한 손실.

### 6.3 재현 가능성 확보 방안

- **공개 데이터셋만** 쓰고, 실행 때 Hugging Face Hub·torchvision에서 자동으로 받는다(`rn50/datasets.py`, 사진 선택 규칙 포함).
- **소규모 평가 묶음**: dev 6종 × 200장(전처리 끝난 256×256 입력, 정답, FP32 텍스트 분류기, FP32 임베딩) + numpy·onnxruntime만 쓰는 `portable_eval.py` + FP32·제출 모델 + sha256 목록. 몇 분이면 돈다(9.2 (가)).
- **모델 파일·sha256 공개**: FP32 `be19a8ad…`, 제출 P2 `e465d10d…`. 제출 파일을 만든 순서의 중간 파일도 모두 Release에 있다: M2rot FP32 `23236123…`(회전 행렬 `3a6391a2…`) → O-B 융합 `79e797c1…` → `quant_pre_process` `506e9fe4…` → 양자화 O-AB `7a01044c…` → GELU 융합 F2 `03f4de18…` → 패치 임베딩 정수화 P2 `e465d10d…`(`e14/make_models_e14.py`, 세 PC에서 만든 파일 sha가 같음). 실행 환경에 따라 사진 몇 장 결과가 다를 수 있어(7.1-3·4) 사진별 예측도 함께 낸다.
- **깨끗한 폴더 재현 확인** (제출 P2, 10/27): 빈 새 폴더에 제출 Release `siglip2-b32-p2-submit-20261027`만 받아 sha256 15개 확인 → `portable_eval.py --no-mem-pattern` 실행. FP32·P2 사진별 예측·cos가 Release 안 기준 결과와 비트 단위로 같았다(`b32/p2/release_check`). 이전 제출 파일 O-AB도 10/23에 같은 방식으로 FP32·O-AB·비교용 M2rot(`9783d7de…`) 모두 기준 결과와 사진 1,200장 예측이 비트 단위로 같고 cos 차이 0이었다(`b32/xplat/repro_check`). 같은 PC에서는 Release와 절차만으로 완전히 재현된다. 새 clone·새 가상환경에서 dev 캐시부터 다시 만들어도 dev 전체 사진별 예측이 같았다(9.1).
- **다른 CPU 재현**: 같은 묶음(1,200장)을 x86 두 대(i7-1165G7 AVX-512 VNNI·Windows, Core Ultra 9 285K AVX-VNNI·WSL2)와 ARM(Jetson AGX Orin)에서 돌려 사진별로 비교했다. FP32는 세 대 모두 같았다. 제출 P2는 x86 두 대 사이에 1장(맞음/틀림 1장)만 달랐고, ARM과는 4~5장(0.4%)이 달랐다. 고화질 평균 Δ는 i7 +0.4, 285K·AGX +0.3%p(사진 1장 차이)다. 이전 단계 O-AB는 ARM과 25~26장(2.2%)이 달랐다(`b32/p2/xplat_i7/compare_p2_3way.json`, `b32/xplat/compare_3way`).
- **dev 전체 다른 PC 재현**: P2 dev 전체는 x86 세 대(i7, 정민 258V, 준용 285K)에서 89.91 / 89.87 / 89.87%다. 258V와 285K는 데이터셋별·구간까지 같고, i7은 CIFAR A·Food·Caltech에서 1~2장 다르다.
- **채점은 배포한 ONNX 파일로** 한다. 처음부터 다시 만들면 PC마다 float64 행렬 곱 반올림이 달라 회전 행렬부터 파일이 달라진다(B/32 같은 레시피 두 PC dev −0.79 / −0.87).

| 측정 도구 및 방법 | ONNX Runtime 1.25.0 CPU, `ORT_ENABLE_ALL`, **제출 실행 설정과 같은 세션 옵션**(C3: `enable_mem_pattern=False`, 나머지 기본값), intra-op 스레드 고정·inter-op 1 (`siglip2/scripts/cross_latency.py --no-mem-pattern`). 피크 메모리: 모델마다 새 프로세스, 4스레드, 세션 생성 + 추론 50회 중 최대 working set. 크기: ONNX 파일 바이트 |

- **대표 실행**: 10/27 저녁 C3 두 실행(20:24, 21:24), 고성능 모드에서 FP32·이전 단계 O-AB·제출 P2 3개를 C3 설정으로 번갈아 1·2·4스레드 × 3세션씩. "대표값은 C3 기준"은 1회째 전에 정했다(학술부 답에 따른 변경, 그때 같은 날 기본 세션 결과 −59.8%는 이미 알고 있었음). 1회째는 test 직후라 세션 2·3에서 FP32 2·4스레드가 18~44% 느려져 4스레드 비율이 부풀었을 수 있어(−64.4%), 2회째를 재기 전에 "두 C3 실행 6세션의 비율 중앙값, 메모리는 두 실행 평균"을 대표값으로 정해 커밋했다(`39a6710`). 2회째 4스레드는 −59.9%였다. 시작 전 CPU 사용률·속도 확인을 모두 통과했고 이상치 규칙은 쓰지 않았다.
- **같은 날 기본 세션 실행**(17:22, 교체 확인용): P2 4스레드 −59.8%, 1스레드 −67.6%, 메모리 −62.6%. C3는 지연을 바꾸지 않으므로(개발 초기 모델에서 잰 E12-1: 1/2/4스레드 0.0 / +0.5 / −1.6%. P2에서는 1스레드가 두 실행에서 −67.6 / −68.3%로 거의 같음) 실행 사이 차이는 실행 간 흔들림으로 보고, 보고서에는 범위(4스레드 세션별 −58~−65%)를 함께 적는다. 같은 날 고성능 모드가 아닌 상태로 시작한 첫 실행은 중단하고 무효로 기록했다.
- **재현 범위로 적은 이전 실행**(6.5 아래 표, 이전 단계 O-AB): 10/23 새벽 실행은 9구간 모두 정상이었다. 10/22 낮 실행은 같은 실행에 함께 넣은 기준 모델(개발 초기 모델 FP32)이 같은 스레드 모든 세션 중앙값보다 10% 넘게 느린 세션을 뺐다(측정 중 정한 규칙). 그 재측정 때 같은 스크립트가 두 번 실행된 사고가 있어 첫 실행 값을 로그에서 복원했다(요약과 일치, 반복별 값은 잃음). 10/22 저녁 실행은 연속 실행 발열로 2·4스레드 절대값이 느리다.
- 주 조건은 결과를 보기 전에 정한 **4스레드**다.
- **세션 설정 C3**: 학술부 답(채점은 팀이 낸 실행 스크립트로)에 따라 제출 실행 스크립트(`portable_eval.py`·`cross_latency.py`의 `--no-mem-pattern`)에 `enable_mem_pattern=False`를 넣었다. 출력은 기본 세션과 비트 동일하다(P2 고화질 5종 × 200장 `b32/p2/c3_equal`, dev 묶음 1,200장의 사진별 예측·cos `b32/p2/xplat_i7_c3`, 이전 O-AB 1,000장). 그래서 기본 세션으로 잰 dev·test 정확도는 C3에서도 같다. 메모리 효과는 측정 정의에 따라 다르고 이 보고서 정의(세션 생성 + 추론 50회 최대 working set)에서는 작다: P2 169.8 → 166.1 MiB(−2.2%, 서로 다른 실행에서 1회씩), 같은 두 실행의 O-AB·FP32는 변화 없음(193.0 / 193.3, 453.9 / 454.1 MiB). 정민 E12-1 정의에서는 O-AB −4.0%(`b32/submit_prep/mem_pattern`).

### 6.6 결과 해석

- **손실은 어디서 생기나**: "거대 값이 눈금을 넓혀 그 층 출력이 무너지는" 손실은 M2·회전으로 해소됐다(M2만으로 −61.0 → −1.6%p, 가장 나쁜 층 SNR 0.8 → 20.5 dB). 남은 손실은 행렬곱을 모두 8비트로 한 데서 오는 작은 임베딩 오차(dev cos 0.988)이고, O-A·O-B로 더 줄었다(같은 바탕 비교, 준용 PC: −0.87 → −0.29, 짝 차이 +0.57 [+0.17, +0.97]. 재반올림 제거와 float Softmax의 효과는 나누지 않았다). 패치 임베딩까지 8비트로 한 P2도 dev 손실을 늘리지 않았다(O-AB 대비 +0.23 [−0.08, +0.53]).
- **취약 입력 ① 비슷한 클래스 경계**: 새 오답은 클래스마다 대부분 1~2장(최대 3장)씩 흩어지고, staffordshire bull terrier ↔ american pit bull terrier, ragdoll ↔ birman처럼 원래 헷갈리는 쌍에서 뒤집힌다. 특정 클래스가 망가진 것이 아니다(이전 주 후보 M2rot 기준 분석, `b32/G3_error_classes`).
- **취약 입력 ② 데이터셋·변형·해상도**: test에서 세밀 구분이 필요한 Cars(−0.45)·Flowers(−0.39)가 구간이 0을 포함하지 않는 작은 손실이고, Pets(−0.19)·Food(+0.04)·Caltech(−0.03)는 거의 그대로다. 입력 변형은 90도 회전에서 P2가 −1.5%p로 유일하게 유의한 손실이다(FP32 자체도 71.9%로 크게 떨어지는 학습 분포 밖 입력, 200장 × 5라 구간이 넓음). 흑백(−0.6)·좌우 반전(−0.6)·어둡게(−0.5)는 유의하지 않다(처방 전 모델은 흑백에서 크게 무너짐, 6.2). 저해상도 CIFAR-100은 오히려 +0.57%p(구간 하한 −0.01로 경계, 이전 O-AB +0.93 유의, 원인 미확인 7.1), ImageNetV2는 −0.43%p로 작지만 유의한 손실이다.
- **dev와 test가 일치한다**: dev −0.05 [−0.41, +0.33], test −0.20 [−0.33, −0.07]. dev에서 구성을 고르며 생길 수 있는 과적합이 test에서 드러나지 않았다(이전 O-AB도 dev −0.27 / test −0.23). test는 표본이 커서 구간이 좁아져 "작지만 유의한 손실"로 나왔다.
- **CPU 속도가 줄어든 곳**: 이 PC 프로파일(10/27, 4스레드, 200장)에서 P2는 O-AB보다 커널 시간 −15%(34.9 → 29.5 ms)다. ## 7. 한계점 및 엣지 디바이스 이식 계획

### 7.1 현재 한계점

1. **속도는 노트북 한 대의 비공식 값이다.** 채점 PC와 팀 공식 측정 노트북에서는 재지 않았다. 같은 PC에서도 실행에 따라 2·4스레드 절대값이 최대 약 48% 달라졌다(4스레드 FP32 61.5 / 88.6 / 83.2 / 60.0 / 68.9 / 68.3 ms). 발열만으로는 설명되지 않아(같은 시각 별도 기준 모델 확인값은 정상) 실행 구성에 따른 CPU 클럭 상태 차이로 추정한다. 그래서 같은 실행 안 비율로만 비교했다. 비율도 세션에 따라 흔들려(10/27 C3 두 실행 4스레드 세션별 −61.5 / −64.7 / −64.4 / −58.1 / −64.8 / −59.9%), P2 4스레드 개선율은 −58~−65% 범위로 읽어야 한다(대표값 −62.9%는 6세션 중앙값). 노트북 전원 모드도 크게 영향을 주는데, 시작 전 자동 확인으로는 걸러지지 않아 사람이 확인했다.
2. **P2는 onnxruntime 전용이다.** com.microsoft 연산(`SkipLayerNormalization` 24개·`FastGelu` 13개)이 들어 있어 다른 ONNX 실행기에서는 돌지 않는다. 학술부 답(10/27)에 따라 채점은 팀이 낸 실행 스크립트(onnxruntime)로 하므로 문제가 없다. 보험으로 표준 연산만 쓰는 M2rot INT8(`3a46ae8a…`, Release에 있음, com.microsoft 노드 0개, dev −0.87, 패치 임베딩은 FP32)로 바꾼다. 이 파일은 제출 P2와 같은 바탕(`23236123…`)이라 본선 HEF와 이어진다. Release의 다른 M2rot(`9783d7de…`)은 이 PC에서 다시 만든 비교용으로, 회전 행렬이 달라 본선 HEF와 이어지지 않는다.
3. **P2는 CPU 명령어 집합에 따라 사진 몇 장의 결과가 다를 수 있다.** 같은 묶음(1,200장)에서 x86 두 대(i7 AVX-512 VNNI, 285K AVX-VNNI)는 1장만 달랐고(맞음/틀림 1장), dev 전체에서는 i7과 258V·285K가 CIFAR A·Food·Caltech에서 1~2장 달랐다(고화질 평균 89.91 / 89.87). 이전 단계 O-AB도 같은 크기였다(1장, dev Cars 1장). 정수 곱 뒤 float으로 내는 커널(`MatMulIntegerToFloat`)의 반올림 차이로 보인다(확인 안 함). 출력을 다시 반올림하는 비교용 M2rot(`9783d7de…`)은 x86 두 대에서 사진별 예측과 cos까지 같았다(`b32/xplat/compare_3way`, 비상 대체 `3a46ae8a…`는 다른 CPU에서 돌려 보지 않음).
4. **ARM에서는 사진 약 0.4%의 예측이 다르다.** Jetson AGX Orin에서 제출 P2는 1,200장 중 4~5장의 예측이 x86과 달랐고(맞음/틀림 3~4장), 고화질 평균 Δ는 285K와 같았다(+0.3). 이전 단계 O-AB는 25~26장(2.2%)이 달랐다. P2는 입력부터 정확한 정수라 첫 float → 정수 경계가 없어진 덕분으로 보이지만 확인하지 않았다. O-AB에서 numpy 버전을 바꿔도 같아 차이는 ORT ARM 정수 커널 쪽으로 보인다(확인 안 함). VNNI가 없는 x86은 확인하지 않았다(reduce_range는 그 포화를 막는 설정이지만 효과는 시험하지 못함).
5. **O-A의 float 출력은 Hailo에서 16비트로 맞추지 않는다(D-051).** HEF는 같은 FP32 그래프를 Hailo 방식으로 따로 양자화하므로 ORT의 "행렬곱 출력 float"과 Hailo의 8/16비트 출력이 다르다. 맞추려면 HEF를 다시 빌드하고 실칩에서 다시 확인해야 해서, 이 차이는 기록만 한다.
6. **CIFAR-100이 FP32보다 높게 나온 원인을 모른다**(P2 +0.57 [−0.01, +1.07], 이전 O-AB +0.93). 저해상도 입력에서 양자화 잡음의 우연한 효과일 수 있다(보조 지표라 선택에 쓰지 않음).
7. **Hailo 손실이 CPU보다 크다**(부록 F.4).
8. **레지스터 캐시는 보정 데이터로 정한 근사다.** dev·test 7종과 입력 변형 8종에서는 근사 손실이 없었지만(FP32 근사 cos 0.9998 이상), 분포가 아주 다른 입력에서는 맞지 않을 수 있다.
9. **원인 분석 일부는 fake-quant다.** 토큰별 눈금 실험은 메커니즘 확인용이라 지금 정수 커널에서 그대로 쓸 수 없다.
10. **90도 회전 입력에서 P2가 작지만 유의한 손실을 보였다**(−1.5 [−2.8, −0.1], 6.2). 8종 중 1종만 유의해 다중 비교의 우연일 수 있지만, 회전된 사진이 많은 쓰임새에서는 따로 확인이 필요하다.

### 7.2 본선 이식 계획 (11/6 ~ 12/4)

본선은 예선 모델(같은 회전 행렬·sink 규칙·레지스터 캐시 상수의 SigLIP2 B/32)을 그대로 쓰고, 예선과 같은 벤치마크·측정 방법(배치 1 지연 주 지표)으로 서버(ORT INT8)와 엣지(Hailo)를 비교한다. 컴파일 과정의 조정은 "예선 대비 변경 사항"으로 기록한다.

### 9.4 재현 시 유의사항

1. **채점은 배포한 ONNX 파일로 해 주십시오.** 처음부터 다시 만들면 PC마다 float64 행렬 곱의 반올림이 달라 회전 행렬부터 파일이 달라지고, dev 정확도가 0.1%p 안팎 달라질 수 있습니다(B/32 같은 레시피 두 PC −0.79 / −0.87).
2. **onnxruntime으로 실행해 주십시오.** 제출 모델에 `com.microsoft` 연산(SkipLayerNormalization·FastGelu)이 있습니다.
3. **정수 커널 결과는 CPU 명령어 집합에 따라 사진 몇 장 다를 수 있습니다.** x86(VNNI) 두 대는 1,200장 중 1장만 달랐고(dev 평균 89.91 / 89.87%), ARM(Jetson AGX Orin)은 4~5장(0.4%)이 달랐지만 고화질 평균은 285K와 같았습니다(7.1-3·4). 비교용으로 이 PC의 사진별 예측 파일을 함께 냅니다. VNNI가 없는 x86은 확인하지 않았습니다.
4. **입력은 0~255 픽셀을 /127.5 − 1 한 값(open_clip 기본 전처리)이어야 첫 층 양자화가 무손실입니다.** 다른 보간으로 정수가 아닌 픽셀 값이 들어오면 입력이 8비트 눈금으로 반올림됩니다(오차는 픽셀 반 칸 이내).
5. **지연은 FP32와 같은 실행에서 비율로 비교해 주십시오.** 절대값은 PC·전원 설정·발열에 따라 크게 다릅니다(7.1-1). 노트북은 고성능 모드·충전 상태에서, 다른 프로그램 없이 재 주십시오. 메모리 수치는 제출 실행 설정(C3: `--no-mem-pattern`) 값입니다(6.4).
6. **처음 실행 시간**: dev 캐시 생성 1~2시간, test 7종(FP32·INT8 함께) 이 PC에서 약 3시간 15분(대기 제외). 빠른 확인은 9.2 (가)를 써 주십시오.
7. **별도 다운로드·디스크**: 텍스트 분류기를 만들 때 Hugging Face `timm/ViT-B-32-SigLIP2-256` 가중치를 처음 한 번 받습니다. ImageNetV2는 `siglip2/scripts/test_g6.sh`가 받습니다. 디스크는 약 20 GB가 필요합니다(원본 데이터 7.0 GB, B/32 전처리 캐시 5.4 GB, Hugging Face 가중치 1.5~2.9 GB, 가상환경 1.1 GB, ONNX·재현 묶음 약 2 GB). GPU는 필요 없습니다.

## 부록 D. 개발 과정 메모

원인(고정 위치 sink 토큰의 거대 활성값)과 처방(레지스터 캐시 + 회전)은 개발 초기 모델(SigLIP2 B/16, 제출 모델 아님)에서 먼저 찾았다. 제출 모델 B/32에서는 같은 진단을 처음부터 다시 했다(5.3). 두 경우 모두 "가장 나쁜 층의 SNR 순서 = 정확도 순서"가 성립했다(`results/siglip2/G8_candidates/b16/generalization/H5_qdq_snr`). 이 모델로 쓴 test 이력은 부록 E에 적는다.

## 부록 E. test 사용 이력

- 제출 모델 B/32: ORT 2회 — 당시 제출 파일 O-AB 1회(10/22, `results/siglip2/G8_candidates/b32/test`), 교체한 P2 1회(10/27, `b32/test_p2`). Hailo 본선 HEF GF와 비교용 Zoo HEF 1회(10/24, 준용 `B32_hef_test` B절). ORT는 제출 파일(D-049, D-052)을, Hailo는 판정 기준·HEF 선택을 test 전에 커밋해 고정했고, 결과로 구성을 바꾸지 않았다. O-AB → P2 교체는 dev 정확도와 지연·메모리만으로 test 전에 확정했고, P2 test 결과와 상관없이 되돌리지 않기로 미리 정했다.
- 개발 초기 B/16 단계 이력: 그 당시 후보 2개(fc2 보호 구성 `5eee7839…`, 10/16~17 `results/siglip2/G6_test`; 회전+M2 `e84c3727…`, 10/19 `results/siglip2/G6_m2rot_ort`)로 각 1회. 제출 모델을 B/32로 정한 결정(D-048)은 이 두 test 뒤에 했지만 근거는 dev와 실칩 dev 결과뿐이다.

## 부록 F. Hailo-10H 실칩 확인 (본선 준비)

본선 이식을 미리 확인한 자료다(학술부 답: NPU 직접 실행 결과도 보고서에 넣어도 됨). 측정은 준용(NVIDIA Jetson AGX Orin + Hailo-10H, HailoRT 5.3.0, DFC 5.4.0)이 했다. **정확도는 모두 실칩 값이다.** 개발 초기 모델에서 같은 HAR의 에뮬레이터는 정상인데 컴파일한 HEF만 실칩에서 무너진 사례(top-1 50.68%, cos 0.31~0.44, `G6c`)와, 저해상도 입력에서 에뮬레이터가 실칩과 맞지 않은 사례(`G5b`)가 있었기 때문이다.

### F.1 컴파일 설정 출처

컴파일 자원 설정은 Hailo Model Zoo v5.4.0 레시피에서 가져왔다. `resources_param`은 SigLIP2 B/32 레시피에서, `allocator_param`·`context_switch_param`은 CLIP ViT-B/16 레시피에서 가져왔다. 이 설정은 양자화 결과를 바꾸지 않았다: 뒤의 두 줄은 G와 GF 출력이 1,200장 비트 동일했고(`G6f`), `resources_param`은 넣기 전후(M과 M_rb) 실칩 출력이 dev 6×200장에서 비트 동일했다(`G6b`). 우리 기여는 16비트 보호층을 줄인 것이다. 회전·레지스터 캐시로 거대 활성값을 없앤 그래프에서는 Zoo가 16비트로 두는 블록 0의 어텐션 출력 투영·fc1·fc2와 블록 5 fc2(`conv3·4·5·25`)도 8비트로 내릴 수 있었다(G, F.3-2). 처방 없는 그래프로 같은 층을 8비트로 내리는 대조 실험은 하지 않았다.

### F.3 정확도 이득은 어디서 오나

1. Zoo 레시피 그대로 회전만 넣은 S1은 Zoo와 동률이다(+0.65 [−0.19, +1.46]). 같은 레시피에 sink 처방을 더한 S2는 Zoo보다 +2.12 [+1.37, +2.89] 우위다(S2 − S1 +1.48 [+0.77, +2.19]). 그 위에 optimization level 1·보정 256장이 +1.05 [+0.50, +1.63]를 더 보탰다(M_both − S2). → 이득의 가장 큰 몫은 sink 처방이고, 레시피 조정도 보탰다. 그래프 출처(open_clip vs Zoo ONNX)는 Zoo 레시피(level 0, 64장)에서 차이를 만들지 않았다(+0.13 [−0.51, +0.72] 동률, `G6d`).
2. 우리 넓은 16비트 보호(M)를 Zoo 집합으로 줄여도 동률이다(−0.21 [−0.70, +0.30], `G6b`). Zoo가 지키는 층까지 8비트로 내린 G는 Zoo보다 +2.67%p 정확하면서 빠르다(F.2).
3. Zoo 컴파일 설정 두 줄(F.1)은 출력을 바꾸지 않고 지연만 줄였다(G → GF −0.70 ms). 컨텍스트 수가 줄어서는 아니며(`G6f`), 어디서 오는지는 확인하지 않았다.
