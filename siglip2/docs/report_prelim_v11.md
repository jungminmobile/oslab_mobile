## 2. 결과 요약

정확도는 제로샷 분류 Top-1 정확도이고, 고화질 데이터셋 5종(Pets, Flowers, Cars, Food, Caltech)의 test 평균을 주 지표로 썼다. 효율은 Intel i7-1165G7 노트북에서 배치 1, ONNX Runtime 1.25.0으로 원본(FP32)과 최적화 모델을 같은 실행 안에서 번갈아 잰 값이다(6.4). 최적화 후 모델은 마지막 단계 이름을 따서 P2라고 부른다.

| 항목 | Baseline (FP32) | 최적화 후 (INT8, P2) | 변화율 |
|---|---|---|---|
| 모델 크기 (MB) | 378.36 | 95.65 | **−74.7%** |
| 파라미터 수 (M) | 94.55 | 94.54 (행렬곱 가중치 94.37M을 INT8로 저장) | −0.02% |
| 연산량 (GFLOPs) | 11.50 | 11.50 (INT8 정수 연산으로 실행) | 0% |
| 추론 Latency (ms, 4스레드 / 1스레드) | 68.6 / 126.0 | 24.7 / 39.2 | **−62.9% / −68.0%**¹ |
| Throughput (FPS, 4스레드 / 1스레드) | 14.6 / 7.9 | 40.5 / 25.5 | **+178% / +222%** |
| 피크 메모리 사용량 (MB) | 476.0 | 174.4 | **−63.4%** |
| 정확도 — Top-1, 고화질 5종 (test) | 88.51% | 88.30% | **−0.20%p** [95% 구간 −0.33, −0.07] |
| 정확도 — Top-1, 고화질 5종 (dev) | 89.96% | 89.91% | −0.05%p [−0.41, +0.33] |

¹ 세션 6번 각각에서 구한 FP32 대비 비율의 중앙값이다. 지연 중앙값끼리 나누면 4스레드 −64.0%로 조금 다르다. 같은 노트북에서도 측정할 때마다 4스레드 비율이 −58~−65% 사이에서 흔들려서 범위를 함께 적었다(7.1). 파라미터 수가 거의 그대로인 것은 가중치를 지우지 않고 INT8로 바꿨기 때문이다.

**요약.**
- SigLIP2 B/32의 이미지 인코더를 재학습 없이 INT8 정적 사후 양자화(PTQ)로 최적화했다.
- 처음에 단순하게 INT8로 바꿨을 때는 정확도가 61%p나 떨어졌다. 원인을 추적해 보니 특정 위치의 토큰 두 개가 아주 큰 활성값을 만들고 있었고, 이를 레지스터 캐시와 Hadamard 회전으로 해결했다.
- 그 뒤 ONNX Runtime의 정수 커널에 맞게 그래프를 네 군데 고쳐서 속도를 더 끌어올렸다. 패치 임베딩을 포함한 행렬곱 80개를 모두 INT8로 바꿨다.
- 결과적으로 크기 −74.7%, 지연 4스레드 −62.9%·1스레드 −68.0%, 메모리 −63.4%를 얻었고, test 정확도 손실은 0.20%p였다.
- 본선 기기인 Hailo-10H에서도 같은 모델을 미리 돌려 보았다. Hailo가 공개한 같은 모델의 HEF보다 지연은 9.5% 짧고 test 정확도는 2.73%p 높았다(부록 B).

## 3. 대상 모델 및 선정 사유

### 3.1 대상 모델

| 구분 | 내용 |
|---|---|
| 모델명 / 버전 | SigLIP2 ViT-B/32, 입력 256×256 (`hf-hub:timm/ViT-B-32-SigLIP2-256`, open_clip 3.3.0 / timm 1.0.30) |
| 모델 유형 | 멀티모달(이미지-텍스트 대조 학습). 이 중 이미지 인코더를 최적화 |
| 저장소 URL | 코드: https://github.com/jungminmobile/oslab_mobile (비공개 저장소, 심사 기간 동안 학술부에 접근 권한 제공) / 원 모델: https://huggingface.co/timm/ViT-B-32-SigLIP2-256 |
| 커밋 해시 또는 릴리스 태그 | 코드: 제출 시점 main 커밋의 태그 `prelim-submit` / 모델 파일: Release `siglip2-b32-p2-submit-20261027` |
| 사전학습 가중치 출처 | Google SigLIP2 [1] 공개 가중치의 timm/open_clip 변환본 (Hugging Face) |
| 라이선스 | Apache-2.0 (Hugging Face 모델 카드) |

모델은 32×32 패치로 사진을 잘라 토큰 64개를 만들고, 폭 768의 Transformer 블록 12개를 거쳐 768차원 임베딩을 낸다. 파라미터는 94,552,320개, 연산량은 11.50 GFLOPs다. 텍스트 쪽은 클래스 이름 임베딩을 FP32로 한 번만 계산해 두면 되므로, 기기에서 사진마다 실행되는 이미지 인코더만 양자화했다.

### 3.2 선정 사유

1. **엣지에서 쓸 곳이 많다.** 사진 임베딩 하나로 분류, 검색, 필터링을 모두 할 수 있다. 분류할 클래스가 바뀌어도 다시 학습할 필요 없이 텍스트만 바꾸면 된다.
2. **최신 모델인데 무겁다.** SigLIP2(2025)는 CLIP 계열의 최신 모델이지만 FP32 이미지 인코더가 378 MB이고, 노트북 1스레드에서 사진 한 장에 120 ms 넘게 걸린다.
3. **양자화가 쉽지 않아서 해 볼 만했다.** 단순 INT8로는 정확도가 무너지는데, 원인을 찾아 고치면 손실을 아주 작게 줄일 수 있었다(5장).
4. **본선 기기에서 비교할 기준이 있다.** Hailo Model Zoo에 같은 모델의 공개 HEF가 있어서, 우리 결과를 벤더의 결과와 직접 비교할 수 있다.

### 3.3 Hailo-10H 호환성 사전 검토

본선에서는 예선과 같은 모델(같은 회전 행렬과 레지스터 캐시 상수)을 Hailo DFC로 컴파일한다. 다만 CPU 제출 파일을 그대로 넣는 것이 아니라, 같은 모델의 표준 연산 FP32 파일을 바탕으로 Hailo 방식으로 따로 양자화한다. 두 FP32 파일은 가중치가 비트 단위로 같다. 5.1의 ⑥~⑧(ORT 커널 맞춤)은 CPU용 변환이라 HEF에는 들어가지 않는다.

| 항목 | 검토 결과 |
|---|---|
| 지원 연산 | Conv, MatMul, Add, Mul, Softmax, GELU, LayerNorm, Reshape/Transpose. 모두 DFC가 지원한다 |
| 비표준 층 | FP32 모델에는 없다. 레지스터 캐시는 상수 곱셈·덧셈 마스크로 만들어서 표준 연산으로 컴파일된다. 제출 ONNX의 com.microsoft 연산은 CPU 배포용이고 HEF에는 쓰지 않는다 |
| 실제 컴파일 | Hailo DFC 5.4.0, `--hw-arch hailo10h`로 컴파일 성공. 입력 정규화까지 HEF 안에 넣었다 |
| CPU Fallback | 없음. HEF가 입력부터 출력 임베딩까지 그래프 전체를 덮는다 |
| 혼합 정밀도 | 패치 경로와 잔차 덧셈 26개만 16비트, 나머지는 8비트. Hailo 공식 설정이 16비트로 두는 층 4개(블록 0·5)도 모두 8비트로 내릴 수 있었다(부록 B). 처방 없는 모델로 같은 대조 실험은 하지 않았다 |
| INT4 | CPU에서는 4비트가 오히려 느려서 쓰지 않았다(5.3). Hailo INT4는 본선에서 시험할 계획이다 |
| 버전 | 팀 DFC 5.4.0(HailoRT 5.3.0에서 실행 확인). 본선 Pi의 HailoRT 버전은 하드웨어를 받은 뒤 확인하고, 다르면 그 버전에 맞춰 다시 컴파일한다 |

예선 제출물에 본선 이식용 FP32 파일(`siglip2_image_fp32_g6b_b32_m2rot.onnx`)도 함께 넣었다.

## 5. 적용한 최적화·양자화 기법

### 5.1 기법 요약

"단독 적용 효과"는 다른 조건을 같게 두고 그 기법만 켜고 끈 결과다. 정확도는 dev 전체의 고화질 5종 Top-1 손실(FP32 대비)이고, ⑥~⑧은 바로 앞 단계 대비 차이, ②는 소규모 dev 묶음의 코사인 유사도다. 지연은 1/2/4스레드 변화율이다. ⑥은 팀원 PC(Core Ultra 9 285K), ⑦⑧은 팀원 PC(Core Ultra 7 258V)에서 잰 값이다.

| 적용 기법 | 적용 대상 | 주요 설정값 | 단독 적용 효과 |
|---|---|---|---|
| ① 정적 PTQ (INT8) | 인코더 행렬곱 79개 | ORT `quantize_static`, QDQ, 가중치 채널별 INT8, 보정 256장 | 이것만으로는 정확도 붕괴 (−60.96%p) |
| ② Percentile 보정 | 활성값 범위 | 99.999 백분위 [9] | MinMax·Entropy보다 좋았다 (fc2 보호 상태 코사인 유사도 0.963 vs 0.931·0.937) |
| ③ 레지스터 캐시 (M2) | 큰 값을 만드는 토큰 2개 | 보정 사진 평균값으로 고정, 토큰 수는 유지 | **−60.96 → −1.58%p** |
| ④ Hadamard 회전 | 잔차 흐름 768채널 | 무작위 부호 Hadamard 직교 회전, LayerNorm 흡수 | ③ 위에서 −1.58 → −0.79%p |
| ⑤ 활성값 UINT8 + reduce_range | x86 정수 커널 | 가중치 7비트 범위 | 부호 있는 INT8 활성값보다 4스레드 약 2배 빠름 (개발 초기 모델 SigLIP2 B/16에서 확인, 제출 모델 아님) |
| ⑥ ORT 커널 맞춤 (O-A + O-B) | 행렬곱 출력, 잔차+LayerNorm | 행렬곱 출력 재반올림 생략, SkipLayerNorm 융합 | +0.57%p 개선, 지연 −4.9 / −8.4 / −11.4% |
| ⑦ GELU 융합 | MLP GELU 13곳 | GELU 노드 9개 → `FastGelu` 1개 | 정확도 차이 없음, 지연 −6.6 / −6.8 / −8.0% |
| ⑧ 패치 임베딩 정수화 | 패치 임베딩 Conv | INT8 행렬곱으로 바꿈, 입력은 픽셀 정수 그대로(무손실) | 정확도 차이 없음, 지연 −5.5 / −4.3 / −4.1%, 메모리 −16.2% |

①~⑧을 모두 적용한 것이 제출 모델 P2다. ①~⑥까지 적용한 바로 전 단계 모델을 O-AB라고 부르는데, P2는 O-AB보다 지연이 8.8~11.8% 짧고 메모리는 12.0% 작았으며(i7 노트북 기본 세션, 제출 설정에서는 지연 8.1~14.8%), 정확도는 차이가 없었다(dev +0.23 [−0.08, +0.53]%p).

### 5.2 양자화 상세

| 구분 | 내용 |
|---|---|
| 양자화 방식 (PTQ / QAT) | PTQ (정적 사후 양자화, 재학습 없음) |
| 정밀도 (INT8 / INT4 / 혼합) | INT8. 행렬곱 80개(패치 임베딩 1 + 인코더 79) 전부 입력·가중치 INT8. Hailo HEF는 8/16비트 혼합 |
| 캘리브레이션 데이터셋 | 고화질 5종의 train 분할에서 dev·test와 겹치지 않게 뽑은 사진 |
| 캘리브레이션 샘플 수 | 256장 (시드 0). 실제로 보정에 들어간 장수를 코드에서 확인했다 |
| 양자화 제외 레이어 | 행렬곱은 제외 없음. LayerNorm, GELU, Softmax, 잔차 덧셈은 float으로 계산 |

보정 장수를 따로 확인한 것은 팀의 다른 실험에서 ORT 보정기가 일부 배치를 조용히 버린 일이 있었기 때문이다.

### 5.3 적용 근거 및 과정

**1) 단순 INT8은 실패했다.** 처음에 ORT 정적 양자화로 모든 연산을 INT8로 바꾸자(MinMax 보정) dev 고화질 정확도가 0.4~3.8%로 완전히 무너졌다. 행렬곱만 INT8로 하고 Percentile 보정을 써도 FP32 89.96%에서 약 29%로 떨어졌다(−60.96%p).

**2) 어느 블록이 문제인지 찾았다.** 블록을 하나씩만 INT8로 바꾸고 나머지는 FP32로 두는 방식으로 민감도를 쟀다(그림 1). 블록 1~4는 거의 영향이 없었지만 블록 0과 5~11은 하나만 바꿔도 크게 무너졌다. 연산별로 보니 범인은 MLP의 두 번째 행렬곱(fc2)이었다. 흥미롭게도 Hailo 공식 컴파일 설정이 16비트로 보호하는 층도 블록 0과 5에 몰려 있었다.

![그림 1. 블록 하나만 INT8로 바꿨을 때 FP32 대비 임베딩 코사인 유사도](F1_sensitivity.png)

**3) 원인은 특정 토큰의 거대 활성값이었다.** 블록 5의 MLP가 사진 내용과 상관없이 항상 15번 패치 토큰의 몇몇 채널에 아주 큰 값을 썼고, 블록 9에서는 7번 토큰에서 같은 일이 생겼다. 블록 5 출력의 최댓값이 중앙값의 약 990배였다. CLS 토큰이 없는 ViT가 패치 일부를 "register"처럼 쓰는 현상으로 알려져 있다[2][3]. 활성값은 텐서마다 눈금 하나로 양자화하기 때문에 이 큰 값에 맞춰 눈금이 넓어지고, 나머지 평범한 값들이 거의 0으로 뭉개진다. 실제로 그 토큰만 빼고 눈금을 정하는 실험(디버깅용 fake-quant)을 해 보니 임베딩 코사인 유사도가 0.997로 거의 원래대로 돌아왔다. 즉 8비트가 부족한 게 아니라 눈금이 맞지 않았던 것이다.

**4) 원인을 직접 고쳤다.** 두 가지를 적용했다.
- 레지스터 캐시(토큰 축)[4][5]: 문제 토큰의 값을 보정 사진에서 구한 평균 상수로 고정했다. 양자화 없이 FP32에서 이 근사만 넣었을 때 정확도 차이는 +0.06%p로 사실상 없었다.
- Hadamard 회전(채널 축)[6][7]: 잔차 흐름에 직교 행렬을 곱해 몇몇 채널에 몰린 큰 값을 768채널로 고르게 퍼뜨렸다. 역회전은 가중치에 흡수해서 원래 모델과 수학적으로 같다.

둘을 따로, 또 같이 적용해 보니(그림 2) 레지스터 캐시가 결정적이었고(−60.96 → −1.58%p), 회전은 그 위에서 조금 더 보탰다(→ −0.79%p). 회전만 쓰면 여전히 붕괴했다(−54.52%p). 예전처럼 문제 층만 FP32로 남기는 방식(−2.36%p)보다 모든 행렬곱을 INT8로 한 지금 방식이 더 정확했다.

![그림 2. 레지스터 캐시(M2)와 회전의 2×2 단독 효과 (dev 전체, 고화질 Top-1 손실)](F2_ablation_2x2.png)

**5) 정말 그 층이 원인이었는지 확인했다.** 배포 파일과 같은 눈금으로 행렬곱 79개의 8비트 출력 SNR을 하나씩 쟀다.

| 구성 | 가장 나쁜 층 SNR (dB) | 평균 SNR (dB) | dev 손실 (%p) |
|---|---|---|---|
| 처방 없음 | 0.8 (블록 9 fc2) | 28.5 | −60.96 |
| 회전만 | 1.0 (블록 9 fc2) | 30.6 | −54.52 |
| 문제 층만 FP32 | 13.1 | 29.0 | −2.36 |
| 레지스터 캐시만 | 14.9 | 29.5 | −1.58 |
| 회전 + 레지스터 캐시 | 20.5 | 31.6 | −0.79 |

평균 SNR은 정확도 순서와 맞지 않았지만, 가장 나쁜 한 층의 SNR 순서는 5개 구성 모두 정확도 순서와 같았다. 가장 나쁜 층 하나가 전체 정확도를 좌우하는 것으로 보이고, 우리 처방은 바로 그 층의 SNR을 끌어올렸다(0.8 → 20.5 dB).

**6) 속도를 위해 ORT 커널에 맞췄다.** 정확도 문제를 해결한 뒤 프로파일을 보니 정수 행렬곱 앞뒤의 양자화·역양자화, 정수 Softmax, 합쳐지지 않은 LayerNorm에 시간이 많이 쓰이고 있었다. 팀원 신준용이 행렬곱 결과를 8비트로 다시 반올림하지 않고 float으로 내도록 바꾸고(O-A), 잔차 덧셈과 LayerNorm을 하나로 합쳤다(O-B). 이 둘은 정확도도 조금 올렸다(+0.57%p). 이어서 팀원 전정민이 GELU를 이루던 노드 9개를 하나로 합치고(⑦), 패치 임베딩 Conv를 INT8 행렬곱으로 바꿨다(⑧). 입력 픽셀이 0~255 정수라서 눈금을 2/255로 잡으면 입력 양자화에서 오차가 생기지 않는다는 점을 이용했다.

**시도했지만 넣지 않은 것.** 판정 기준은 결과를 보기 전에 정해 두었다.

| 시도 | 결과 | 넣지 않은 이유 |
|---|---|---|
| 블록 0을 FP32로 보호 | 손실 −0.79 → −0.42%p | 개선이 통계적으로 유의하지 않은데 지연 +5.9%, 크기 +20.6% |
| 가중치 4비트 | 크기는 더 줄어듦 | x86 CPU에서 오히려 1.36~2.05배 느렸다 (개발 초기 모델에서 확인) |
| 문제 층만 FP32로 남기기 | −2.36%p | 전부 INT8인 지금 방식이 더 정확하고 작다 |
| O-A만 / O-B만 적용 | 일부 기준 미달 | 둘을 함께 적용했을 때만 기준을 모두 통과 |
| 활성값 INT8(부호 있음) | 정확도는 같음 | x86에서 행렬곱이 정수로 합쳐지지 않아 FP32만큼 느림 (개발 초기 모델에서 확인) |
| 패치 임베딩을 FP32 행렬곱으로 | 출력은 Conv와 같음 | 오히려 느려짐(4스레드 +3.7%) |

### 6.2 벤치마크 선정 사유 및 타당성

- **분야가 다른 세밀 분류 5종을 평균했다.** 동물, 꽃, 자동차, 음식, 일반 사물처럼 성격이 다른 데이터를 고른 것은 한 분야에만 맞춘 결과가 나오지 않게 하기 위해서다. 비슷한 클래스를 구분해야 하는 데이터라 작은 임베딩 오차도 정확도에 드러난다.
- **프롬프트는 CLIP 논문의 공식 템플릿[8]을 썼다.** SigLIP 권장 템플릿과 dev에서 비교해 보니 CLIP 템플릿이 1.77%p 높았다.
- **보조 지표는 따로 적었다.** CIFAR-100은 32×32 사진을 키운 것이라 앞쪽 층 변화에 지나치게 민감해서 설정을 고르는 데는 쓰지 않았다. ImageNetV2는 일반적인 사진에서도 괜찮은지 확인하는 용도다.
- **고르지 않은 대안**: ImageNet-1k 검증셋은 등록해야 받을 수 있어 재현이 어렵다고 보고 공개된 ImageNetV2를 썼다. 이미지-텍스트 검색은 텍스트 인코더의 영향이 섞이고, linear probe는 추가 학습이 필요해서 제외했다.
- **데이터를 구간별로 나눴다.** 보정은 train 사진으로, 설정 선택은 train에서 떼어 낸 dev로만 했다. test는 설정을 고르는 데 쓰지 않았다. 다만 정직하게 밝히면, B/32 모델로 test를 쓴 것은 ORT에서 두 번이다. 처음에는 그때의 최종 후보 O-AB로 한 번 쟀고, 그 뒤 팀원이 ⑦⑧을 찾아 P2를 만들었을 때 dev와 속도만 보고 P2로 정한 뒤 한 번 더 쟀다. 두 번 모두 평가할 파일과 판정 기준을 test 전에 커밋해 고정했고, test 결과를 보고 설정을 바꾸지 않았다. 참고로 O-AB의 test 손실은 −0.23%p로 P2(−0.20%p)와 유의한 차이가 없었다. Hailo 쪽 test는 한 번 썼다. 그 전에 개발 초기 모델(B/16) 단계에서도 후보 두 개로 test를 한 번씩 썼고, 그 뒤 B/32로 모델을 바꾼 결정은 dev와 실칩 dev 결과만 보고 했다.
- **통계**: 같은 사진끼리 짝지은 부트스트랩(1,000회)으로 95% 신뢰구간을 냈고, 구간이 0을 포함하지 않으면 유의한 차이로 봤다.
- **흔들림도 확인했다.** 보정 사진의 시드를 바꿔도 dev 손실은 −0.79 / −0.80 / −0.70%p로 거의 같았다(회전+레지스터 캐시 단계). 사진을 뒤집거나 흑백으로 바꾸는 등 입력 변형 8종에서는 90도 회전만 작지만 유의한 손실(−1.5%p)이 있었고 나머지 7종은 유의한 손실이 없었다.

### 6.3 재현 가능성 확보 방안

- 데이터셋은 모두 공개 데이터다. 대부분은 실행하면 Hugging Face와 torchvision에서 자동으로 받고, ImageNetV2만 스크립트(`siglip2/scripts/test_g6.sh`)로 따로 받는다. 어떤 사진을 dev로 쓸지는 이미지 해시로 정해서 누가 돌려도 같다.
- 전체 데이터를 받지 않아도 되도록 **소규모 평가 묶음**을 만들었다. dev 6종 × 200장(전처리 끝난 입력과 정답, FP32 텍스트 분류기)과 numpy·onnxruntime만 쓰는 스크립트 `portable_eval.py`를 Release에 함께 넣어서, 몇 분 안에 FP32와 P2를 비교할 수 있다(9.2 (가)).
- 모델 파일은 sha256과 함께 공개했다(FP32 `be19a8ad…`, P2 `e465d10d…`). 빈 폴더에 Release만 받아서 실행해 보니 사진별 예측까지 기준 결과와 비트 단위로 같았다.
- 다른 CPU에서도 돌려 보았다. i7 노트북에서 이 묶음의 결과는 FP32 고화질 88.9%, P2 차이 +0.4%p, 코사인 유사도 0.9884였다. 같은 1,200장에서 FP32는 x86 두 대와 ARM 한 대에서 모두 같았고, P2는 x86 두 대 사이에서 1장, ARM과는 4~5장(0.4%)이 달랐다. 정수 커널의 반올림 차이로 보인다. 그래서 i7 노트북의 사진별 예측 파일도 함께 냈다.
- 채점은 우리가 배포한 ONNX 파일로 해 주길 부탁한다. 처음부터 다시 만들면 PC마다 회전 행렬 계산의 반올림이 달라 파일이 조금 달라진다.

### 6.4 측정 프로토콜

| 측정 조건 | 설정값 |
|---|---|
| 입력 해상도 | 256×256 (open_clip 기본 전처리) |
| 배치 크기 | 1 (엣지에서 사진 한 장씩 처리하는 상황). 정확도 평가만 배치 50 |
| Warm-up 횟수 | 모델마다 20회 |
| 측정 반복 횟수 | 사진 200장 × 3회를 FP32와 최적화 모델이 번갈아 실행, 이것을 세션 3번 × 스레드 1·2·4로 반복 |
| 통계 방식 (평균 / p50 / p95) | 세션마다 장당 평균을 구하고 세션 중앙값을 대표값으로 씀. p50·p95도 기록 |
| 측정 도구 및 방법 | ONNX Runtime 1.25.0 CPU, `ORT_ENABLE_ALL`, 스레드 수 고정, `siglip2/scripts/cross_latency.py --no-mem-pattern`. 피크 메모리는 모델마다 새 프로세스에서 세션 생성과 추론 50회 중 최대 사용량 |

- **왜 번갈아 쟀나**: 처음에는 모델을 하나씩 따로 쟀는데, 같은 모델도 잴 때마다 결과가 크게 달랐다. 노트북 CPU 클럭이 상황에 따라 바뀌기 때문이었다. 그래서 FP32와 최적화 모델을 같은 실행 안에서 번갈아 돌리고 비율로 비교했다.
- **대표값**: 10/27 저녁 두 번의 실행(세션 6개)에서 비율의 중앙값을 썼다. 첫 실행에서 FP32 쪽이 일부 세션에서 유독 느려져 비율이 부풀었을 가능성이 있어서, 두 번째 실행 전에 "두 실행을 합친 중앙값을 쓴다"고 정해 두고 다시 쟀다.
- **세션 설정**: 학술부에서 채점은 팀이 낸 실행 스크립트로 한다고 답해 주셔서, 제출 스크립트에 메모리를 아끼는 ORT 옵션(`enable_mem_pattern=False`)을 넣었다. FP32도 같은 옵션으로 쟀다. 이 옵션은 출력을 바꾸지 않고(사진 1,200장 결과가 비트 단위로 같음), 지연에도 영향이 거의 없다(개발 초기 모델에서 −1.6~+0.5%). 그래서 아래 값과의 차이는 옵션 효과가 아니라 실행마다 생기는 흔들림으로 본다. 옵션을 넣기 전 같은 날 잰 결과는 4스레드 −59.8%, 1스레드 −67.6%, 메모리 −62.6%였다. 대표값의 기준을 이 옵션으로 바꿀 때 이 결과를 이미 알고 있었다는 점도 함께 밝힌다.

### 6.6 결과 해석

- **정확도 손실은 대부분 해결됐다.** 큰 손실의 원인이던 거대 활성값은 레지스터 캐시와 회전으로 없앴다(가장 나쁜 층 SNR 0.8 → 20.5 dB). 남은 손실은 행렬곱을 전부 8비트로 바꾸면서 생기는 작은 임베딩 오차(코사인 유사도 0.988)이다.
- **어떤 사진에서 틀리나**: 회전+레지스터 캐시 단계 모델로 분석해 보니, 새로 틀린 사진은 특정 클래스에 몰리지 않고 클래스마다 1~2장씩 흩어져 있었다. 원래도 헷갈리는 쌍(예: 스태퍼드셔 불 테리어와 아메리칸 핏불 테리어, 랙돌과 버먼 고양이)에서 답이 뒤집히는 경우가 많았다.
- **데이터셋별로 보면**: 세밀한 구분이 필요한 Cars(−0.45%p)와 Flowers(−0.39%p)에서 작지만 유의한 손실이 있었고, Pets·Food·Caltech는 거의 그대로였다. 저해상도인 CIFAR-100은 오히려 0.57%p 올랐지만 통계적으로 유의하지는 않았고(구간 −0.01~+1.07) 원인도 찾지 못했다. 일반 사진인 ImageNetV2는 −0.43%p로 작지만 유의한 손실이 있었다.
- **dev와 test 결과가 일치한다.** dev −0.05%p, test −0.20%p로, dev로 설정을 고르면서 생길 수 있는 과적합은 보이지 않았다. test는 사진 수가 많아 구간이 좁아져서 "작지만 유의한 손실"로 나왔다.
- **속도가 어디서 빨라졌나**: 프로파일을 보면 P2는 O-AB보다 커널 시간이 15% 줄었다(34.9 → 29.5 ms). 줄어든 곳은 GELU 연산과 FP32 패치 Conv였고, 정수 행렬곱 시간은 그대로였다. 지금은 커널 시간의 절반 이상(53%)이 정수 행렬곱이다.
- **스레드가 많을수록 배속이 작다**: 1스레드에서는 3.2배 빨라졌지만 4스레드에서는 2.5~2.8배였다. 토큰이 64개뿐이라 float으로 남은 연산의 비중이 상대적으로 커진 탓으로 추정한다(따로 확인하지는 않았다).

## 7. 한계점 및 엣지 디바이스 이식 계획

### 7.1 현재 한계점

1. **속도는 노트북 한 대에서 잰 비공식 값이다.** 같은 노트북에서도 실행에 따라 FP32 절대 지연이 최대 약 48%까지 달랐다. 그래서 같은 실행 안의 비율로만 비교했는데, 비율도 세션마다 −58~−65% 사이에서 흔들렸다. 전원 모드도 결과를 크게 바꿔서 측정 전에 직접 확인했다.
2. **제출 모델은 onnxruntime에서만 돈다.** 속도를 위해 onnxruntime 전용 연산(SkipLayerNormalization, FastGelu)을 썼기 때문이다. 채점이 우리 스크립트(onnxruntime)로 진행되니 문제는 없지만, 혹시 몰라 표준 연산만 쓰는 INT8 모델(dev −0.87%p)도 Release에 함께 두었다.
3. **CPU 종류에 따라 사진 몇 장의 결과가 다를 수 있다.** x86 두 대 사이에서는 1,200장 중 1장, ARM과는 4~5장이 달랐다. 평균 정확도에는 거의 영향이 없지만 완전히 같지는 않다. VNNI 명령어가 없는 x86 CPU에서는 확인하지 못했다.
4. **Hailo에서는 CPU보다 손실이 크다.** Hailo는 같은 FP32 모델을 자기 방식으로 따로 양자화하기 때문에, CPU용으로 한 ⑥~⑧이 들어가지 않는다. test 손실이 CPU는 0.20%p, Hailo는 1.04%p였다.
5. **레지스터 캐시는 보정 사진으로 정한 근사값이다.** FP32에서 이 근사만 넣었을 때는 우리가 써 본 데이터셋과 입력 변형에서 차이가 없었지만(코사인 유사도 0.9998 이상), 분포가 아주 다른 사진에서는 맞지 않을 수 있다.
6. **90도 회전된 사진에서 작은 손실이 있었다**(−1.5%p). 8종 중 하나라 우연일 수도 있지만, 회전된 사진이 많은 상황이라면 따로 확인이 필요하다.

### 9.4 재현 시 유의사항

1. 채점은 Release에 올린 ONNX 파일로 부탁드립니다. 처음부터 다시 만들면 PC마다 회전 행렬의 반올림이 달라 결과가 0.1%p 안팎 달라질 수 있습니다.
2. 제출 모델에 onnxruntime 전용 연산이 있으므로 onnxruntime 1.25.0으로 실행해 주십시오.
3. 입력은 0~255 픽셀을 /127.5 − 1 한 값(open_clip 기본 전처리)이어야 패치 임베딩의 입력 양자화에 오차가 생기지 않습니다. CPU 종류에 따라 사진 몇 장의 결과가 다를 수 있습니다(7.1). 비교용으로 i7 노트북의 사진별 예측 파일을 Release에 넣었습니다.
4. 지연은 절대값보다 FP32와 같은 실행에서 잰 비율로 봐 주십시오. 노트북은 충전기를 연결하고 고성능 모드에서 다른 프로그램 없이 재는 것이 좋습니다.
5. 처음 실행할 때 Hugging Face 모델 가중치를 한 번 받고, ImageNetV2는 `siglip2/scripts/test_g6.sh`로 받습니다. dev 캐시 생성에 1~2시간, test 7종에 약 3시간이 걸리고, 디스크는 약 20 GB가 필요합니다. 빠르게 확인하려면 9.2 (가)를 써 주십시오. GPU는 필요 없습니다.
